## 一、这是什么

**Audio Mixing（局域网声音投射）**：把同一个局域网里任意设备**正在播放的声音**，
送到任意一台或多台设备上播放。

- **不经过服务器**、不注册、不登录、不上传数据
- **免虚拟声卡**（Windows 用 WASAPI 回环，手机用 MediaProjection + AudioPlaybackCapture）
- **免安装**：Windows 单文件 exe（20.5 MB）+ Android 单文件 APK（114 KB）
- 两端都开源（MIT），两端都零第三方依赖

**用户的核心诉求（原话，务必遵守）**：
1. 「是局域网内使用哦。你不要搞的像 oopz 那种软件一样是跨网络使用」→ **不做跨网穿透**
2. 「我并非永久不换设备。这个程序也要服务于其他人，不能搞专项优化」→ **不许针对特定设备写特例**
   （有一条测试专门盯着这件事：代码/文档里出现特定机器名会让测试变红）
3. 「手机不准经过电脑，要独立」→ 手机之间直连，电脑只是局域网里的另一个节点
4. 「我要求的是各设备**可调节**的音量条」→ 每台设备的音量要能单独调
5. **如实告知**：做不到的事、有限制的事，要在界面上写明，不要假装成功

## 十、★ 协议说明（改任何通信代码前必读）★

### 10.1 音频包头：28 字节，小端

```
偏移  类型      字段          说明
 0    uint16   magic         0x574C（'W','L'）
 2    uint8    version       1（★ 不要改，改了对方直接丢包）
 3    uint8    ptype         1=AUDIO 2=HELLO 4=PING 5=PONG 6=BYE 7=STATS
 4    uint8    flags         0x01 不连续 / 0x02 最后一块 / 0x04 静音
 5    uint8    codec         2=PCM16（手机只认这个）3=Opus
 6    uint16   seq           包序号
 8    uint32   ssrc          流标识
12    uint32   samples       ★ 本包帧数（历史坑，见 10.3）
16    uint64   ts_ns         发送时刻墙钟纳秒
24    int16    gain_q14      音量，Q14 定点（1.0 == 16384）
26    uint16   payload_len   负载字节数
```

- 48kHz / 立体声 / 每包 **480 帧 = 10ms**
- PCM16 时一包负载 = 480 × 2 × 2 = **1920 字节**
- **手机端接收准入的主判据是【负载长度】**：`plen > 1920` 才拒；`== 1920` 收；`< 1920` 收下并补零

### 10.2 端口与发现

```
17800  TCP   网页面板
17830  UDP   设备发现（组播 239.255.77.120 + 子网广播 + 对已知设备额外单播；两端唯一需要一致的端口）
47831  UDP   音频（收发同一个端口）
```

信标是 JSON（≤1200 字节），字段：`wl / id / name / platform / version / audio_port / web_port / sources / sinks / busy`。
每 2 秒发一次，15 秒没收到就从列表移除。**手机端的 node_id 必须持久化**（曾经每次启动新建 UUID，
导致电脑端列表里同一台手机堆出三条记录）。

### 10.3 ★ `samples` 字段的坑（花了一整天才找到）★

- **历史 bug**：电脑端把它填成了**累计帧偏移**（`480 × 包序号`），手机端把它当**本包帧数**校验
  → 手机把电脑发来的包**全部拒收**（10266 个），表现是"电脑在发、手机一个包都收不到"。
- **为什么一直没暴露**：Python 接收端**根本不读这个字段**（它按解码后的负载长度算帧数），
  所以电脑↔电脑完全没有症状。
- **现在的状态（两端都改过，互相兼容）**：
  - 电脑端填**本包帧数**（480）
  - 手机端**不以它为拒绝依据**，只作参考；矛盾时在诊断报告里写一句人话
- **教训**：跨端协议的每个字段，**语义必须写死在文档里**，并且要有跨语言对拍。
  详见 `docs\协议-samples字段语义.md`。

### 10.4 控制包（`T_STATS`，ptype=7）的 JSON 字段

用于两端互报状态，也是**自动收听**与**音量同步**的载体（两端字段名必须一致）：

| 字段 | 类型 | 语义 |
|---|---|---|
| `want_listen` | bool | "我在送声音给你，请求你自动打开收听"。**幂等**，没有取消消息 |
| `gain` | 0.00~1.50 | **我→你** 这条链路的共享音量 |
| `gain_ts` | int 毫秒 | 上面那个值最后被修改的时刻（**谁后改谁赢**） |
| `gain_rx` | 0.00~1.50 | **你→我** 这条链路的共享音量 |
| `gain_rx_ts` | int 毫秒 | 同上 |

- **老版本收到这些键当未知字段忽略即可**（不新增包类型、不改包头）
- 时间戳要**整数解析**（踩过坑：借道 float 会把 13 位毫秒戳截断成 1.7e8，"谁后改谁赢"直接失效）
- 值一样时**不要回推**；本机正在拖动时不抢；本地 5 秒没动过则采纳对端（防时钟偏差）

## 十一、★★ 最值钱的部分：踩过的坑（每条都花过时间）★★

```
【协议层】
· samples 语义没写死 → 两端理解不同 → 手机拒收全部包（见 10.3）
· 手机端只认 PCM16 + 恰好 480 帧，且不做重采样（宁可不要也不要变速变调）
· 电脑端广播不是"往广播地址盲发"，而是【逐个单播给发现列表里的每个节点】
  → 所以"互相看不见"时，广播会发给 0 个目标（表面看像"广播没实现"）

【打包/构建】
· PyInstaller 的 onefile 启动器会被杀软拉黑（报"Could not create temporary directory!"）→ 换 Nuitka
· Windows Store 版 Python 缺链接库，打不了包 → 必须用 python.org 官方版
· Nuitka 打包后 Opus 找不到 dll：opuslib_next 内部用 ctypes.util.find_library，
  而它在 Windows 上【只沿 PATH 查找】，os.add_dll_directory 对它无效
  → 必须把 dll 目录加进 PATH 并预加载
· appcompat 会拖进旧版 kotlin-stdlib，和 AGP 撞出一堆 Duplicate class
  → 安卓端刻意零依赖，主题用系统主题，UI 全用代码写
· javac 默认按平台编码读源码（中文 Windows 是 GBK）→ 中文会乱码
  → app/build.gradle 里显式设 options.encoding = "UTF-8"
· Java 连【注释里】的 \uXXXX 都会在词法分析前解析 —— 注释里写错形式直接编译失败
· PowerShell 会把 -Dfile.encoding=UTF-8 这种带点带等号的参数拆开 → 必须加引号

【行为/时序】
· 抖动缓冲：nextSeq = -1 是哨兵值（表示"等第一包"），任何无条件自增都会毁掉它
  → 断流一次就再也不出声
· 压延迟逻辑"每 tick 只丢一帧然后 return"：对方每 10ms 正好来一帧
  → 收一帧丢一帧，缓冲深度永远降不下来 → 全程静音（实测 5946 个包里丢了 5908 个）
· 清理"已经走了的目标"如果只挂在【界面 tick】上：手机一锁屏 tick 就停
  → 电脑关掉后手机还在一直发（隐私问题）→ 必须挂到【后台定时】
· 发现层：安卓 Wi-Fi 省电会大量丢组播/广播帧（实测 74 秒只收到 8 个信标，对方发了约 37 个）
  → 对策：组播 + 广播 + 对已知设备【额外单播】三管齐下
· 前端有一份重复定义的同名函数覆盖了前一份 → "每 4 秒刷新"变成死代码

【验证方法】
· 验证工具本身会骗人（check_apk.py 在 GBK 控制台崩过）
· debug APK 的哈希不可复现（同一份源码两次构建哈希不同）
· 成品时间戳必须晚于所有源码（否则可能交付不含改动的包）
· 多 agent 并行时：同一时刻只能有一个 writer 写同一个文件；
  ★ 给一个"已停止"的 agent 发消息会把它唤醒 ★（会造成多人同时写同一个文件）

【环境】
· 这台机器上，由自动化工具启动【新建的 exe】会被安全软件拦截
  → 所以"双击运行"这件事只能由用户做，自动化只能在源码层验证
  （但 python / java / gradle 这些已安装的签名程序是可以跑的）
```
