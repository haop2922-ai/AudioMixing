# 排查实录：一个改名需求引发的三小时事故

这份文档记录 2026-10-10 那天真实发生的一次事故链。**代码一直是好的，102 项测试一直全绿**，
但交付却反复失败 —— 问题全出在**排查方法**上。改这个项目之前建议先读一遍。

---

## 结论先放前面（三条铁律）

```
① 验证"exe 能不能跑" → 让【用户双击】。绝不用自动化工具自己跑一下就当结论。
② 排查时一次只改一个变量。同时改打包方式 + 目录 + 配置路径 = 永远查不出来。
③ 动工作区【外面】的任何东西（C 盘、%APPDATA%、注册表、防火墙）之前先问。
```

## 一、环境类坑（这台机器特有，但很典型）

### 1. 安全软件拦的是【调用者】，不是【被调用的程序】

火绒的拦截日志原文：

```
系统防护,系统加固,DeepSeek Harness.exe 触犯敏感动作防护规则, 已阻止
防护项目：隐藏执行PowerShell
操作进程：E:\AI\DEEPSEEK\DeepSeek Harness.exe
操作结果：已阻止
```

**含义**：火绒有规则「隐藏执行 PowerShell」—— 它拦的是**由非交互进程启动的 powershell**。
当自动化工具（AI Agent、CI、脚本调度器）用 pwsh 去启动 exe 时，**整条调用被拦**，
于是你看到的"程序打不开"，其实是"我的调用被拦"。

**教训**：
```
✗ 不要用自动化工具的运行结果，判断"这个 exe 对用户能不能跑"
✓ 同一个文件，让用户双击一次 —— 那才是真实结论
✓ 判断依据：同一个文件换调用者，结果不同 → 问题在调用链，不在文件
```

**怎么一次性验证**：把**同一个文件**（哈希一致）放在两处分别试：
```
用户双击 Downloads\App.exe      → 秒开 ✓
工具运行 App\App.exe            → 失败 ✗
→ 哈希相同 ⇒ 文件没问题 ⇒ 是调用环境被拦
```

### 2. 同一个目录里反复编译，会让整个目录变得"不干净"

在同一个目录里编译几十次（每次 PyInstaller 都生成全新 exe）会不断触发安全软件规则，
累计之后该目录里的**单文件 exe** 会打不开（它们启动时要往 `%TEMP%` 解压，解压动作被拦）。

**规避**：
```
✓ 编译输出换到独立目录（build\ 与源码分离）
✓ 交付目录里只放最终产物，不要放编译中间件
✓ 交付目录里【只留一个】exe，避免用户选错
```

### 3. 单个目录被"路径级"防护规则盯上（本次事故的真凶，2026-10-11 用对照实验确认）

**症状**：同一个 exe（哈希完全相同）在不同目录表现完全不同：

```
C:\Users\75341\Desktop\xxx.exe          → 秒开 ✓
E:\xxx.exe                              → 秒开 ✓
E:\AI\deep blue\xxx.exe                 → SmartScreen 审查后被关闭 ✗
```

**原因**：在一个目录里**反复编译**（本次是几十次 PyInstaller / Nuitka 构建，每次都生成全新 exe），
会不断触发安全软件（火绒自定义防护 / HIPS）的规则，最终**整个目录**被纳入它按路径绑定的拦截范围。
之后该目录里的**任何**新 exe 都会被拦 —— 与文件本身无关。

**同时注意**：这类软件还会拦**自动化工具自身**的动作。本次日志原文：

```
系统防护,系统加固,DeepSeek Harness.exe 触犯敏感动作防护规则, 已阻止
防护项目：隐藏执行PowerShell
```

→ 后果是：**自动化工具自己去"验证" exe 永远失败**，而**用户双击同一文件却成功**。
本次为此浪费了数小时，方向全错。

**正确做法（三步，一步都不能省）**：

```
① 让【用户双击】验证，不要用自动化工具的运行结果下结论
② 症状对不上时，第一件事做【同一文件换位置/换调用者】的最小对照
③ 交付产物【不要】放在编译目录里 —— 编译目录只放源码和中间产物
   交付物放桌面 / 普通目录 / 安装包，用户拿到就能跑
```

**根治办法**：把该目录从安全软件的"自定义防护 / 路径规则"里移除；
或者在**另一个目录**里编译（编译目录与交付目录分离）。

### 3b. SmartScreen 与"网络标记"（更正早前写错的结论）

早前本文档写过"把文件的网络标记清掉就不会再弹 SmartScreen" —— **不准确** ✗。
实测结论：

```
· 从 zip 解压 / 从浏览器下载的文件会带 [ZoneTransfer] ZoneId=3 标记 ✓
  → 一定触发 SmartScreen（这一步确实和标记有关）
· 但【没有标记】的未签名新 exe 也可能被拦 ✗
  → 原因是 SmartScreen 还看【文件信誉】：未签名 + 该哈希从没被放行过 = 弹窗
· 用户点过一次「更多信息」→「仍要运行」之后，系统按【该文件的哈希】记住决定
  → 同一文件之后永久不弹 ✓；改动一个字节 / 换个名字 → 新哈希 → 又弹一次 ✓
```

**所以结论**：未签名程序"第一次弹一次"是 Windows 的正常行为，**清标记不能根治**，
唯一根治办法是**买代码签名证书**。分发时告知用户"点一次仍要运行"即可。

### 3c. 打包器被拉黑时：换打包器比换参数有效

本次 PyInstaller 打的单文件 exe 一律报 `Could not create temporary directory!`
（单文件模式启动时必须创建临时目录并解压自己 → 该动作被拦）。
**换参数、换目录、清标记、改配置目录全都无效** ✗。

**改用 Nuitka 后一次通过** ✓：

```bash
python -m nuitka --onefile --assume-yes-for-downloads ^
  --enable-plugin=numpy --windows-console-mode=disable ^
  --include-package=audiomixing --include-package-data=pyogg ^
  --include-package-data=opuslib_next --include-package-data=qrcode ^
  --include-data-dir=audiomixing/ui=audiomixing/ui ^
  --output-filename=AudioMixing.exe audiomixing_launcher.py
```

产物 20.3 MB（PyInstaller 版 34 MB），启动机制与 PyInstaller 的 bootloader 完全不同，
没有被安全软件的"连坐拉黑"命中。**教训：打包器的 bootloader 也会进黑名单，换一个往往直接绕开。**

**注意**：Nuitka 需要标准 python.org 的 Python（微软商店版**不提供链接用库文件** ✗，
会报 `unable to find dynamic system library 'python313'`）。


### 4. 窗口版 vs 控制台版（PyInstaller）

```
--windowed   没有控制台窗口，更"干净" → 但报错时只弹一个对话框，看不到原因 ✗
--console    带一个黑窗口 → 报错直接打在窗口里，排查快得多 ✓
--onefile    单文件，启动时解压到 %TEMP%\_MEIxxxx → 解压被拦就死 ✗
--onedir     一个文件夹（exe + _internal），不解压 → 更抗拦 ✓ 但文件多、启动慢 ✗
```

**教训**：**先把 `--console` 版跑通，确认功能没问题，再考虑要不要换成 `--windowed`**。
遇到"闪一下就没了"，第一步永远是**编一个带控制台的诊断版**看真实报错。

## 二、改名类坑

### 5. `import wavelink` 和 `import wavelink.engine` 是两种写法

用正则 `\bwavelink\.` 批量替换时，**只匹配带点的**，
于是 `import wavelink`、`from wavelink import x` 这种**裸导入全被漏掉** ✗

**正确做法**：
```python
src = src.replace("import wavelink\n", "import audiomixing\n")
src = src.replace("from wavelink import", "from audiomixing import")
# 再做带点的（from wavelink.engine import …）
```

### 6. 内部名字和外部名字要分清

```
对外名字（用户可见）  exe 名、窗口标题、托盘提示、文档、防火墙规则名 → 必须统一
内部名字（用户看不到）Python 包名、配置目录、协议魔数、端口
```

**内部包名不对外** —— 不发布到 PyPI 就永远不会和别人冲突。
但**内外一致**可以省掉长期维护的心智负担，所以值得改，只是**不值得为它冒险**。

### 7. 配置目录改名必须带迁移

```python
def _migrate_old_dir(new_dir: Path) -> None:
    """把旧的 %APPDATA%\\WaveLink 整棵复制到新目录（只做一次）。"""
    import shutil
    try:
        old = new_dir.parent / "WaveLink"
        if new_dir.exists() or not old.is_dir():
            return
        shutil.copytree(old, new_dir, dirs_exist_ok=True)
    except Exception:
        pass        # 迁移失败不影响启动
```

**不做迁移的后果**：用户更新完程序，所有路由和设置凭空消失。

**副作用要提前说**：旧版和新版各用一份配置 → 两边设置独立 →
**建议用户只用其中一个版本**，别来回切。

## 三、代码健壮性坑

### 8. 程序不该因为"存不了设置"就崩

```python
# 改前：写不进去 → 抛异常 → 程序启动即死（现场表现：双击弹个错就没了）
p.parent.mkdir(parents=True, exist_ok=True)
tmp.write_text(...)
tmp.replace(p)

# 改后：写不进去就跳过，用内存里的默认设置继续跑
try:
    p.parent.mkdir(parents=True, exist_ok=True)
except Exception:
    return p
try:
    tmp.write_text(...)
    tmp.replace(p)
except Exception:
    return p
```

**任何"启动路径上的写文件"都要能失败而不致命** —— 权限、磁盘满、杀软拦截、
只读介质，都会让这一行抛异常。

## 四、排查方法坑（最值钱的一节）

### 9. 第一句话就问："你双击打不开，还是我运行打不开？"

这一句话能在第一分钟定位问题。当天我跳过了它，于是花了三小时。

### 10. 一次只改一个变量

当天我同时改了：打包方式 + 输出目录 + 配置目录 + exe 名字。
结果任何一个环节出问题都无法单独验证。

**正确顺序**：
```
改 1 个 → 验证 → 记录结论 → 再改下一个
```

### 11. 对照实验要用"最小的差异"

当天最有效的两个对照，都不是我想出来的，是**用户**做的：

```
同一个哈希的文件，换位置 → 结论：位置或调用环境是变量
用户双击 vs 工具运行   → 结论：调用者是变量
```

**做对照时把相同的东西列出来，让唯一不同的那个变量自己跳出来。**

### 12. 不要连续"修"一个还没被证实的问题

```
现象 → 假设 → 验证假设 → 再动手
✗ 现象 → 假设 → 直接改代码 → 又出新现象 → 再假设 → 再改 …
```

当天从"exe 打不开"直接跳到"改打包方式"，中间**跳过了验证**。

## 五、交付纪律（避免用户选错）

```
✓ 交付目录里【只放一个】可双击的 exe
✓ 附带一份 README 写清"双击哪个文件、需要哪些同伴文件"
✓ 文件夹版本要说明【必须整个文件夹一起用】不能只拷 exe
✓ 有多个版本时，用清楚的名字区分（旧版备用 / 新版），不要同名
✓ 每改一次交付结构，都自己按用户视角走一遍：打开目录 → 我该点哪个？
```
