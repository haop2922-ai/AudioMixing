# 参赛材料：作品介绍

> 题目：请尽量详细地介绍您的作品，便于评委进一步了解

## 一、核心功能与亮点

这个作品最初是为了一件小事：台式机在客厅放音乐，我想在厨房用手机听，又不想开给整屋。现成办法要么要服务器，要么在 Windows 上装虚拟声卡推流，配一次要半小时。Audio Mixing 只在局域网里把任意一台设备的声音送到任意几台设备的耳机或音箱，不经过服务器、不装虚拟声卡，22 MB 单文件双击就能用。

现有四件主要功能。一是设备间互送：采集、编码、UDP、对端抖动缓冲、按路由混音、多设备输出，电脑与电脑、电脑与手机都通；和「一台电脑当电台」的星形软件不同，这里每台机器都既能当音源也能当喇叭，路由表整个局域网共享，在哪台改都生效，给客厅和书房各放一副耳机不必再买分线器。二是点对点与广播，加「智连」自动接听：点对点只送指定一台，广播是一个人说、所有开收听的人都能听，智连让接收方自动接、多台都接、静音不挂、断流才挂。三是关系图：左进右出，Wi-Fi、蓝牙、广播分色，拖卡合并成同一台设备，点「拆开」还原；设备一多，人记不住谁在给谁送声音，图是唯一能一眼看出来的地方。四是手机端三档送声与音量链路：可以只送不出声，也可以边送边外放，两端合计只乘一次，解决「手机上已调小、电脑那头又小一遍」。

支撑这些的是几件不太看得见的工作：28 字节跨语言包头，Python 与 Java 各实现一份，字段含义用断言冻结；25～150 ms 自适应抖动缓冲；PING 往返时钟对齐；deviceId 主键加旧 id 别名；音频帧带 originId 和 hop 防环。桌面端用 Nuitka 加 zig 打单文件，强制 `-mcpu=baseline`，发布前扫 `.text` 段确认 AVX-512 指令 0 条——真出过「我这台正常、别人一启动就非法指令」。

## 二、TRAE 的具体帮助

TRAE 更像一个能自己跑命令、写测试、也会说「这条我没验」的搭档，不是补全框。有三件事它参与得最深。

一是广播被误判成点对点。手机开广播、电脑开收听，两边界面正常，耳机没声。旧判据看统计包里的 `want_listen`，为真就当对方在单独点送，广播流被「未接受的点对点」闸门拦掉；手机先单独送过电脑再开广播会残留这个字段，所以只在特定顺序下出现。当时两条路：继续在接收端猜发送端意图，或让发送端把意图说清楚。我选后者，只认显式声明的 `send_mode` 和 `broadcast`，并定了「拿不到字段就放行」的退化规则，宁可多听，不能静默失败。TRAE 把两道闸改成同一判据，补了四条回归；这套判据留在了引擎里，后来每次改送声逻辑都要过这四条。

二是单文件版自启动写错路径。勾了自启动、重启不起。Nuitka onefile 不设 `sys.frozen`，`sys.executable` 指向 `%TEMP%` 里每次都不同的解包目录，写进注册表的就是下次开机不存在的路径。关键是判断「什么才算用户双击的那颗 exe」：按 `__compiled__.original_argv0`、`sys.argv[0]`、`sys.executable`、再用 `NUITKA_ONEFILE_PARENT` 反查父进程的顺序找，落在 `onefile_` 临时目录的候选一律丢弃，全丢光就明确报错。TRAE 实现了这段过滤，还补上取消勾选时清旧值；单文件版的自启动现在指向用户双击的那颗 exe。

三是测试污染真实配置。`verify_exe` 早期直接启动打包好的 exe 调接口，把用户 `%APPDATA%` 里的节点名和路由改了，还在局域网留下测试节点——这比功能 bug 严重，因为用户什么都没做。我没有选「事后手工恢复」，而是让验证从一开始不碰真实目录：临时 `AUDIOMIXING_HOME` 沙箱，前后各取一次真实配置指纹比对；现在 13 项检查里就有一项「用户配置未被改动」。

门禁不是一开始就有。2026-11-04 一次清理误删了 225 个归档成品，86 个再也找不回来，之后才把「只增不删」和逐份哈希写进流程。现在发一版要过 486 条单测、打包后 13 项冒烟、双节点 34 项自测、APK 逐份哈希，以及四个交付位 exe 的哈希比对。

## 三、印象最深的一次经历

印象最深的是「音量到底断在哪一环」。真机上手机音量调小一半，电脑那头只剩四分之一左右，像平方。这条线追了五六轮。

第一轮怀疑电脑端键匹配：上报的 key 有 deviceId、IP、别名三种，一处对不上查表就落回 1.0。第二轮怀疑采集时机：若手机在系统音量之后采集，PCM 已带衰减，电脑再乘就是第二次。两种解释都说得通，但都只是解释；最难的一环是承认前两轮都还停在猜测，必须先造一个能判真假的观测。

转折点是把现场数据摊开。我让程序把上报值、命中键、收到峰值、混音峰值、播放系数一起打出来，连续采样。数字很干净：vol 是 0.00，命中键对，电脑系数也是 0.00；关键是增益之前的收到峰值也是 0.00。553 秒、约 106 MB 的 PCM 本身就是全零，电脑没把它乘没，声音在送到之前就没了。

接着做反向验证：保持播放器和 App 内部音量不变，只用音量键改系统媒体音量，看乘音量之前的 `raw_peak` 和之后的 `post_peak`。`raw_peak` 一直是 0.3662，`post_peak` 从 0.0916 到 0，与 vol 的 4096、3072、2048、1024、0 五档严格成正比。一个比例同时证明：采集点在系统音量之前，手机必须乘一次；电脑再乘就是第二次。两个猜测，一个对了一半，一个完全错了。

最后落成一条不变式：两端合计只乘一次。手机把音量绑到送声档位，外放档乘系统媒体音量，静音档只留 App 内部增益；电脑看到来源声明就返回 1.0。它后来写成三处门禁：电脑侧链路检查、手机侧 21 条纯逻辑断言、APK 字段检查。我留下的习惯是，先找能把两种解释分开的那一个数，再改代码；否则改对了也不知道为什么对。
