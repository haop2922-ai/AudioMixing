## 一、结论先行

截图里最明显的问题有两个，都在本轮修掉了：

1. **幽灵卡片还在图上**：本机右侧挂着两张 `不在线 / 不可达` 的节点，还拖着线。
   它们来自两条指向旧 id 的路由（`missing` = 身份确实不存在；以及设备被 `prune` 淘汰后只剩 `offline` 的路由）。
   现在**关系图只画当前真的在设备列表里的端点**：查不到就不画这条边，也不再现造 `不在线 / 不可达` 卡片。
   路由仍保留在路由表里（可删，也可一键「清理失效路由」）。
2. **颜色被状态抢走了**：这两条本是 Wi-Fi 链路，却被画成**红色虚线** —— 而红色在图例里的
   含义是「回环」。现在改成 **颜色只表示链路种类**（Wi-Fi 蓝 / 蓝牙绿 / 广播橙，同一链路永远同色），
   **状态只用线型/透明度表达**（暂无数据压到 55%、离线压到 30%、失效不上图）。
   红色重新只属于回环。

左进右出本身是**对的**（截图里本机在左、去向在右，箭头指向右边），本轮只是把判定依据写清楚并加了回归测试。

### 3.2 布局判定（左进右出）

| 环节 | 代码 | 作用 |
|---|---|---|
| 定层级 | `relComputeRank()`：Tarjan 强连通分量 + 最长路径，`rank[b] = rank[a] + 1` | 边方向上的目标层级永远比来源大；互送形成的真回环同层 |
| 定列号 | `relAutoPos()`：`x: Math.round(22 + r * span)` | 层级 0 在最左，层级越大越靠右 —— **来源左、去向右** |
| 画线 | `relDrawLinks()`：`b.x > a.x` 时 `relPath(a.x + REL_W, y1, b.x, y2)` | 从**源卡片右边缘**画到**目标卡片左边缘**，`marker-end` 指向接收方 |
| 自环 | `if(a === b) return;` / `if(u === v) return;` | 同一台设备（含 WiFi/蓝牙归一后）不画自环 |

截图证据：本机在左、两张去向卡片在右，箭头朝右 —— 方向本身没问题。
本轮的 `missing` 跳过只是让不该存在的节点不再被造出来，不改变列号规则。

## 八、没做到 / 只能真机确认（如实）

1. **"幽灵卡片真的消失"** 只在代码断言 + 静态检查层面验证；需要用户用同一份配置在真机界面上确认。
2. **颜色观感**（蓝/绿/橙 + 透明度是否一眼可辨）需要真机截图确认。
3. **消失时机**：`missing` 有 60 秒宽限（`ROUTE_STALE_AFTER_S`）；`offline` 的旧设备要等到
   `DiscoveryRegistry.prune()` 淘汰它（默认 60 秒没有信标）后才从图上消失 —— 这两种都不是即时消失，
   是为了容忍 Wi-Fi 抖动，不是 bug。
4. 本轮**没有**处理截图左边缘被裁掉的卡片（那属于画布平移/用户拖拽的位置状态，点「重排」复位）。
5. 打包日志提示 `audiomixing/ui` 里还留着一份旧 `AudioMixing-手机版-v2.13.apk` 会被带进 exe；
   它不影响本轮交付（六份交付 APK 都是 v2.14），但属于历史遗留，未在本轮清理。
