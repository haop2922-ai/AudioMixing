## 一、★ 铁律（用户明确要求过的，违反会被直接指出来）★

```
① 【只做局域网】不做跨网络穿透。用户原话：
   「是局域网内使用哦。你不要搞的像 oopz 那种软件一样是跨网络使用」
   → 一旦跨网络就必须有中转服务器，那就不再是这个产品了。不要把"支持远程"当增强需求。

② 【不对特定设备做专项优化】用户原话：
   「我并非永久不换设备。这个程序也要服务于其他人，不能搞专项优化」
   → 代码、注释、文档、测试里【不许出现具体设备型号名】
     （有一条测试专门盯着这件事：出现特定机器名会让测试变红）
   → 需要针对某类设备时，写"设备类别"或能力判断，不写型号

③ 【手机不准经过电脑】用户原话：「手机不准经过电脑，要独立」
   → 手机之间直连；电脑只是局域网里的另一个节点，关掉它手机之间照样能用
   → 例外：网页版手机直连（p2p.html，WebRTC）确实借电脑转发信令，
     那是"不想装 App 的手机"的备用方案，与定位有冲突，是否保留待定

④ 【如实告知，不许假装成功】
   → 做不到的事、有限制的事，写在界面上；采不到声音就说采不到，不要给个空进度条
   → 数据显示要正确。真实教训：曾经出现"上面写丢 0、下面写丢 5908"，
     排查时被误导很久 —— ★ 数字错了比没有数字更坏 ★

⑤ 【每台设备的音量要能单独调】用户原话：「我要求的是各设备可调节的音量条」
   → 滑块（可调）+ 电平条（实时显示）两个都要有
   → 音量分层：系统音量（只显示，绝不修改）× 播放器自己的音量 × 我们这一层（滑杆调这个）
     ★ 我们绝不去动系统音量 ★（有回归测试守着这条）

⑥ 【交付规矩】
   · 桌面只留一个能用的成品，旧版本删掉
   · 成品同时放 release\GOGO\
   · 每个版本备份到 版本备份\<版本号>-<时间戳>\
   · ★ 手机 APK 必须同步 6 处 ★（清单见主文档第六节，最容易漏 installer_payload 那份）
   · 每次交付核对：所有副本 sha256 一致 + 成品时间戳晚于所有源码

⑦ 【每次更新必须写修复明细】用户明确要求：
   「每次更新都必须详细的写明 bug 的存在位置，产生原因和修复手段」
   → 任何一次改动（电脑端 / 手机端，哪怕一行）都要在 `docs\BUG修复明细.md` 末尾追加一条；
     五件事缺一不可：位置（文件+函数+行号）、现象、代码级原因、修复（贴关键判断）、回归（测试名）。
   → 目的：`C:\Users\75341\Desktop\31` 是基于旧版复刻的另一个项目，它会读我们的新版本；
     写清楚是为了让它照抄判断逻辑，而不是只抄版本号。
   → ★ 不要修改 `C:\Users\75341\Desktop\31` ★ 它不属于本仓库，只读。

⑧ 【打包出来的软件必须是"用户独立可用"的】
   → 成品里不许带开发者自己的配置、测试路由、测试设备名、测试端口、测试日志。
   → 手工联调一律 `AUDIOMIXING_HOME=<临时目录>` + 非常用端口，跑完即关；
     绝不允许拿用户真实的 `%APPDATA%\AudioMixing\config.json` 做测试。
   → 发布前必须用"全新临时配置 + 非常用端口"启动一次成品 exe，确认：
     `/api/routes` 为空、`/api/peers` 没有历史设备、配置文件是新建的干净文件。
   → 交付文档里不出现别的项目路径（如 `Desktop\31`）；示例设备名用中性的
     「书房电脑 / 客厅音箱」，不要用开发时的真机名。
   → 测试/构建留下的 `%TEMP%` 沙箱、仓库 `.tmp`、`__pycache__`、日志都要清掉；
     `python tools\audit_leftovers.py --fix` 只删测试路由，**绝不能整份删除用户 config**。

⑨ 【每轮不只修用户点名的三条，必须双端全面自查】
   → 每轮至少覆盖：生命周期与资源释放（引擎/接收器/发送器/投屏/AudioTrack/WifiLock）、

     端口与自动重启、并发与锁、权限与安全、交付物独立性。
   → 查出的问题按 P0/P1/P2 处理：P0 必须当轮修；P1 能修就修；P2 至少写进修复明细并说明。
   → 自查要给出"文件+函数+行号"证据；只有猜测的标"未证实，需真机/日志"。
   → 可以用多个 agent 并行读代码，但**同一时刻只允许一个 writer 写同一个文件**
     （见十条教训第 10 条）。

## 二、标准工作循环（照着走，不要跳步）

```
① 读懂现状
   · 先看有没有相关文档：docs\ 下每个版本都有一份 md 说明改了什么、为什么
   · 看 git log（有完整历史，每条提交都写了"改什么+为什么"）

② 改之前想清楚"改哪个文件"
   · 电脑端：audiomixing\*.py + audiomixing\ui\index.html
   · 手机端：android\app\src\main\java\com\audiomixing\app\*.java
   · ★ 不许动的文件：Proto.java 的【包头布局与版本号】、build.gradle、AndroidManifest.xml（除非明确要改）
   · ★ 同一时刻只改一个文件层级，改完立刻测；不要一次改五个文件再一起测

③ 改完立刻跑（★ 这一步绝不能省 ★）
   · 电脑端改动  → python -m unittest discover -s tests（458 项）
   · 手机端改动  → 六条门禁 + gradle + check_apk
   · 改了协议字段 → 必须重跑跨语言对拍（Java 与 Python 的包 hex 要逐字符相同）
   · 改了界面    → check_ui_syntax.py + check_page_js.py
   · 改了设备列表 / 卡片文案 / 本机身份 → python tools\check_ui_residue.py
     （2026-11-06 新增：测试节点名「自启动复验」、本机卡片混进局域网列表、
       "Wi-Fi 还没测到"这类肉眼可见的残留，单测抓不到，这个门禁抓得到）

④ 构建
   · exe：$env:PYTHONIOENCODING="utf-8"; python tools\build_nuitka.py --test
     （默认单文件 onefile；不要用 --onedir 交付）
   · APK：见主文档 6.2

⑤ 交付前自检（★ 七件事，缺一不可 ★）
   · 所有副本 sha256 一致
   · 成品时间戳晚于所有源码（防止交付不含改动的包）
   · 构建日志里 AVX-512(zmm) 指令 0 条（v2.2 起强制；构建机支持 AVX-512 不代表目标机能跑）
   · 新增的逻辑有对应的回归测试（这个项目是靠测试积累可信度的）
   · ★ `docs\BUG修复明细.md` 已追加本次每一条修复（位置/现象/原因/修复/回归）★
   · ★ `python tools\audit_leftovers.py` 0 error；测试路由/临时沙箱/仓库 scratch 已清 ★
   · ★ 用全新临时配置 + 非常用端口启动成品 exe，确认路由表/设备列表为空、配置为新文件 ★
   · ★ `python tools\check_ui_residue.py` PASS（对真实配置与运行实例各跑一次）★
   · ★ 用成品 exe 本体真实渲染截图（tools\capture_ui_screenshots.py），逐张用图判断 ★
     —— 单测只能证明字段对，不能证明"看上去对"；用户看到的错误都是图上的错误

⑥ 交付 + 告诉用户"用哪个测、测哪几步、每步应该看到什么"
   · 用户会真机测，然后把结果或截图发回来
   · ★ 他发回来的截图/诊断报告往往直接包含根因 ★ 要认真读数字，不要只看描述
```

## 三、★ 与用户协作的方式（他很懂技术，也很较真）★

```
· 他会给出【现象】而不是【原因】。你的任务是找到原因，不是照着他的猜测改。
  ★ 他的猜测方向常常是对的，但机制可能不同 —— 要自己验证。
    真实例子：他说"电脑端音量条改动无效"，我猜"netmic 不是路由"；
    实际是【手机的声音根本没走路由，被收编成频道音源了】—— 方向对、机制不同。
· ★ 他会纠正你，而且往往你是错的。★
  真实例子：我把 PCM 带宽算成 1536 KB/s（实际 1536 kbit/s = 192 KB/s，大了 8 倍），
  是 agent 纠正我的，而且它拒绝按我的错数字去写界面文案（"那会为了吓人而失真"）。
  → 给用户任何数字之前，先算一遍单位。
· ★ 他要求"如实告知"。★ 宁可说"我不知道"或"这只有真机能验"，
  也不要写"应该没问题"。
· 他不需要看过程，需要看【结论 + 证据 + 我做不到的部分】。
  汇报结构建议：改了什么 / 证据（真实输出）/ 你该测什么 / 我证明不了什么。
· ★ 他手上有真机，你没有。★ 凡是"会不会出声""好不好看""手感如何"，
  明确写"只有你能验"，并给他一个【可观察的判据】（看哪个数字、哪个开关、哪个颜色）。
· 他会连续提需求，一次可能四条。逐条确认、逐条落地，不要合并成一条含糊的承诺。
```

```
★ 手机端六条离线门禁（170 项断言，在 android\tools\）

## 六、★ 十一条教训（每一条都真实发生过，别再犯）★

```
1. 【验证工具本身会骗人】每次跑都顺手设的编码变量，掩盖了脚本在纯环境下的崩溃。
   → 凡是"照文档跑不通"，先怀疑文档或工具，不要凑一个能跑的命令。

2. 【debug 包的哈希不可复现】同一份源码两次构建哈希不同（签名块 + zip 时间戳）。
   哈希只用于"标识这一个文件"，判断合格要看内容。

3. 【成品时间戳必须晚于所有源码】曾经编译完之后源码又被改了，差点交付不含改动的包。

4. 【跨端协议的字段语义必须写死】samples 那个坑花了一整天才找到，
   因为 Python 接收端根本不读它，电脑↔电脑毫无症状。

5. 【清理逻辑不要只挂在界面上】手机一锁屏 tick 就停 → 电脑关掉后还在发（隐私问题）。
   要挂到后台定时。

6. 【哨兵值不能被无条件运算破坏】nextSeq = -1 表示"等第一包"，任何自增都会毁掉它。

7. 【丢一帧然后 return 是危险模式】对方每 10ms 来一帧时，收一帧丢一帧，
   状态永远不收敛 → 全程静音。要一次处理到目标状态再继续。

8. 【发现层在安卓上不可靠】实测 74 秒只收到 8 个信标（对方发了 37 个）。
   组播 + 广播 + 单播兜底，三管齐下。

9. 【界面数字口径要一致】"上面写丢 0、下面写丢 5908"会误导排查很久。

10.【多 agent / 多文件并行时】同一时刻只能有一个 writer 写同一个文件；
   ★ 给一个"已停止"的 agent 发消息会把它唤醒 ★（会造成两人同时写同一文件）。
   交接给人类或 AI 时也一样：先清点"现在谁在写"。

11.【测试遗留和"用户独立可用"是交付的一部分】（2026-11-02 用户当场指正）
   → 联调直接跑真实 config，监控页就会留下 `sync-test` 之类的路由；
   → 每跑一轮测试就在 `%TEMP%` 留一批 `am-blocked-*`；
   → 审计工具还把"用户自己改过的端口"当测试残留，`--fix` 差点整份删掉配置。
   现在：测试沙箱统一 `_mkdtemp()` + 退出清理；审计只删测试路由；发布前用干净临时配置验成品。
```
