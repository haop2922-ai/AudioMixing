## 二、严重 ① 与 ② 逐条

### A1（① 隐私/串音）未知来源在「单播放端」时仍被兜底收下

- **位置**：`audiomixing/engine.py` `_attach_stream_routes` L5115-5131；`_reattach_stream_routes` L5147-5149；`audiomixing/net/rtpaudio.py` `Receiver._admitted` L685-696；`engine.py` `_stream_is_accepted` L2715-2729。
- **触发条件**：
  1. 手机用点对点把声音送到电脑，电脑**没有**为它建任何具名路由；
  2. 电脑的发现表里恰好没有这台手机的信标（Wi-Fi 丢信标 / AP 隔离 / 手机换了 IP / 电脑刚启动）→ `registry.resolve(host)` 返回 `None` → `info.node_id = ""`；
  3. 电脑当时只有一个播放端（`len(self.sinks) == 1`）。
- **实际后果**：`_admitted()` 对"认不出来源"一律放行（L691-696 `if not node_id: return True`），`routes_for_sender("")` 返回空集，随后 L5118 的兜底 `routes = set(self.sinks)` 把它挂到那唯一一个播放端上 —— **用户没开「接受」、也没开「只听」，仍然听得到这台手机的声音**。这正是用户 Q2 报告的第二种路径：上一轮只堵住了"认得出身份"的那条（`_sender_is_known` 判断），认不出身份的仍从兜底进来。
- **证据**：`tests/test_audiomixing.py` L4990-5013 的既有测试明确断言"真认不出身份、又只有一个端，才允许兜底"——它把"认不出身份"当成了"手动对端"，但代码无法区分"手动对端"与"任何未知 IP"。
- **修法**：兜底只给**用户手动添加的对端 IP**（`_is_manual_peer(host)`，L1265-1275 已有该判定）；其余未知来源一个端都不挂。为此给 `StreamInfo` 增加 `host` 字段（重挂流时也要能判断），`_on_stream_start` 里写入 `addr[0]`。
- **兼容性**：不影响广播→只听（通配路由依旧兜住未知来源）；不影响手动 IP 对端（仍然兜底）；老手机 2.9 不需要改。

### A2（② 时钟/永久偏移）ClockSync 的 offset 被最小 RTT 冻死

- **位置**：`audiomixing/proto.py` `ClockSync.update` L296-308，核心是 L302 `if rtt <= self._best_rtt or self.samples == 0`。
- **触发条件**：采集过若干轮 PONG 之后，`_best_rtt` 已是历史最小值；此后任何一轮 RTT 只要比它大 1 微秒，`offset_ns` 就不再更新。对端随后发生墙钟校正（NTP 跳变、用户改时间）时，真实 offset 变了而本机仍用旧值。
- **实际后果**：`_play_at = capture_local + target` 整体偏移到错误时间轴；偏移大于 `JITTER_IDLE_NS`/容量时，抖缓持续溢出（`dropped_overflow` 增长）或整段延迟，表现为"突然没声音/声音延迟一秒多/爆音"，直到重启进程。手机上 NTP 校正、切换飞行模式后自动校时都会触发。
- **证据**：L302 的条件是"≤ 历史最小值"，不是"接近最小值"；`_best_rtt` 只减不增（L305），数学上后续永不再命中的概率接近 1。现有测试 L182-198 只覆盖单次同步，没有覆盖"同步后再校时"。
- **修法**：两条更新通道 —— ① 常规：`rtt <= best_rtt * 1.5`（窗口而非严格最小值）；② 硬重锚：`|offset - 当前 offset| > 250ms` 时立即采用并把 `_best_rtt` 重置为该样本 RTT（对端校时就是这种跳变）。小抖动仍走平滑，不引入噪声。

### A3（③ 计数被破坏 + 重复包入缓冲）

- **位置**：`audiomixing/net/rtpaudio.py` `_handle_audio` L783-791（内联统计）；对照 `audiomixing/proto.py` `StreamStats.observe_seq` L340-354（正确口径）。
- **触发条件**：
  - 乱序：旧包 `delta > 0x8000` 时，L785 不计数，但 L787 **无条件** `info.last_seq = pkt.seq` 把游标退回到旧序号；下一个正常包于是算出 `delta = 几十~几百`，`info.lost` 被凭空加几十。
  - 重复：`delta == 0` 时既不丢也不计数，继续 `buf.write(...)`，10ms 音频被写第二遍。
- **实际后果**：诊断页「丢包」虚高（用户会把网络判成差），以及重复包造成一次 10ms 的重复播放 + 缓冲深度上涨（长时间累积会让 target 自适应误判）。
- **证据**：同一个项目里 `observe_seq` 已经写对了（`delta > 0x8000 → return 0` 且**不**更新 `last_seq`），接收端却用了另一份旧的、有缺陷的内联实现。Wi-Fi 重传/多路径会造成乱序与重复。
- **修法**：接收端改为复用 `StreamInfo` 上的同一口径：`delta == 0` → 计 `duplicates` 并直接返回（不写缓冲）；`delta > 0x8000` → 写缓冲但不更新 `last_seq`、不计数；其余按 `delta - 1` 计丢包。诊断里增加 `重复` 计数。

### A4（④ 功能/音量语义）具名多源路由只用第一台的音量

- **位置**：`audiomixing/engine.py` `_peer_media_volume_source` L2661-2684（L2683 命中第一个就 `return`）。
- **触发条件**：一条具名路由的 `from` 写了多台设备（例如两台手机同时送进同一个播放端）。
- **实际后果**：整条路由的 gain 被"最先命中"的那台手机的音量缩放；另一台调到静音不会生效，或一台调小把两台都压小。
- **证据**：`_apply_sink_gain` 把该返回值作为整条 sink 的乘数（L2744-2756），一个 sink 只有一份 gain。
- **修法**：遍历所有具名 token，取**最小值**（保守：不允许任何一台被别的来源顶到更大音量），返回值保留最早命中的键名并注明多源。单源路由结果不变（现有回归测试 L7703 不受影响）。

### A9（③ 数据被破坏）路由增益原样接收 `NaN` / `Infinity`

- **位置**：`audiomixing/engine.py` `_normalize_route`（改前 `"gain": float(raw.get("gain", 1.0))`）；`audiomixing/webui.py` 的路由 POST 直接把它交给 `set_routes()`。
- **触发条件**：向 `/api/routes` POST 一条 `{"gain": NaN}` 或 `{"gain": Infinity}`。Python 的 `json.loads` **默认接受** `NaN` / `Infinity` 字面量（不是标准 JSON，但标准库放行），`float()` 也照收。
- **实际后果**：`apply_gain` 把 NaN/inf 乘进每一声采样，`MultiOut` 输出整条变成 NaN —— 听感是"该路彻底没声音"，而且 NaN 会留在渲染链里，**改回正常增益也不恢复，必须重启**。
- **证据**：同一函数的 `sink_device` / `source_device` 也原样透传任意 JSON 类型（对象/数组），后续按字符串比较时会 `TypeError`，异常落在渲染线程里被吞掉，表现为该路静音。
- **修法**：`as_gain()`：非有限值 → 1.0，其余夹到 `[0, 8]`；`as_text()` 保证设备字段一定是字符串。
- **回归**：`test_a_non_finite_route_gain_cannot_poison_the_sink`（NaN/inf/−inf→1.0、100→8.0、−5→0.0、对象设备字段→字符串）。

## 五、第 5 轮（真机复测三条：Q1 回退 / Q2 音量平方 / Q3 三档）

### 背景与范围

用户在真机上复测出 3 条问题，其中 **Q1 是上一轮 A1 修复引入的回退**（广播+收听无声），
优先级最高。顺序：Q1 → Q2 → Q3。版本：PC 仍 2.21（补齐，不升号）；手机 2.11 / versionCode 25。

### Q1（回退）：广播 + 收听被准入闸门误杀

- **触发链（哪一行把广播拒了）**：
  1. 手机 `Engine.stats()`：`wantListen = targeted`，而 `targeted = sendIds.contains(电脑 id)`；
     广播模式下 `sendIds` 可能残留（先点过「送声音」给电脑、再开广播，旧代码不清集合）。
  2. 电脑 `engine.py` `_handle_peer_requests()`：`if msg.get("want_listen"): self._peer_targeted[node_id] = now`。
  3. 旧 `_peer_sends_point_to_point()` 读 `_peer_targeted` → 返回 True。
  4. `routes_for_sender()` 不给这条流挂 `channel` 通配路由（返回空集）。
  5. `_stream_is_accepted()`：没有具名已接受路由 + "是点对点" → False。
  6. `Receiver._recv_loop` 的 `_admitted()` 在进流表前丢包 → 广播一帧都没进抖缓。
- **修**：新增 `_peer_send_mode`（node → (send_mode, broadcast, at)），只认手机 stats 的
  `send_mode` / `broadcast` 显式声明；`broadcast=true` 永不算点对点；字段缺失（2.10/2.9）
  → 返回 None → **放行（能听）**。删除 `_peer_targeted` 推断（死代码一并清掉）。
  `routes_for_sender()` 的 wildcard 兜底与 `_stream_is_accepted()` 共用同一个
  `_peer_sends_point_to_point()`，不会一处放行一处拒绝。
- **测试（自动可验证，两条同时存在）**：
  - `test_broadcast_listen_receives_real_audio_packets_end_to_end`：A 广播、B 只开收听 →
    `_admitted()` True 且 B 流表 `packets>=1`；同用例点对点未接受 → `_admitted()` False、流表空。
  - `test_a_broadcast_from_a_known_sender_still_reaches_the_channel`（广播 + 残留 want_listen）。
  - `test_a_legacy_phone_that_never_reports_its_mode_is_still_heard`（老手机缺字段 → 能听）。
  - `test_unaccepted_point_to_point_is_not_attached_to_the_channel`（未接受点对点仍拒绝）。
  - `Test20261103GhostsAndStats` 18 项 OK。

### Q2：手机音量被乘两次（平方衰减）

- **判据**：比较手机上报 `vol` 与该流实际收到峰值（`JitterBuffer.peak`，增益前）。
  10 秒窗口 + 窗口内峰值取最大；`vol` 变化 ≥0.15 才比较。
  峰值比 ≈ vol 比 → **采集端已衰减 → 系数 1.0（不叠加）**；
  峰值比 ≈ 1 → 采集在音量之前 → 仍乘；样本不足/静音段 → 不提交（按旧行为叠加）。
  首次判定立即生效，推翻要连续 2 次一致（滞后）。
- **开关**：`Config.phone_volume_mode` = auto（默认）/ off / on；`/api/settings` 校验；
  设置页下拉；设备卡片诊断行 `vol=x.xx  收到峰值=y.yy  判定=…（系数 z.zz）`。
- **测试**：新增 3 项（衰减 → `gain == 路由增益`；不衰减 → `gain == 路由增益 × 0.5`；

### 8.1 结论先行（改前 → 改后）

| 项 | 改前（v2.21 / 2.11） | 改后（v2.22 / 2.12） |
|---|---|---|
| 自动接听 | 接收方开智连也不会自动接；只有发送方单方面判断 | 接收方开智连 → 对端一送就自动接；发送方不需要开 |
| 多台同时送 | 只接一台，其余排队/被拒 | 每台各一条自动收听路由，全接、不排队 |
| 挂断判据 | 单一超时（12s 对端静默 / 30s 停流宽限），静音也会被挂 | **双判据**：音频包静默 ≥4s **且** 心跳消失 ≥4s；静音仍有包 → 不挂 |
| 手动关收听 | 只删路由，下一包又自动打开 | 同请求内先摘智连再删路由；下一包不再打开，等人工重开 |
| 广播 + 智连 | 可组合 | PC/手机所有入口一律拒绝；按钮置灰并显示原因 |
| 手机处理 PC 请求 | 完全忽略（单向） | 处理 `listen_req`（start/stop）并回 `listen_ack_id/action/reason` |
| 路由主键 | `node_id`（端点/IP/MAC 的产物） | `device_id`（设备自生成、持久化、可备份）；旧 id / `manual:IP` 降级为 `aliasIds` |
| 同一手机 WiFi+蓝牙 | 两个节点，可能互相指向绕成环 | 同一 `deviceId` 的多条链路合并为**一个**节点（`hosts` 记多地址） |
| 换机搬数据 | 无法识别 | `instanceId` 不同 → 标 `identity_conflict`，**绝不自动合并** |
| 防自环 | 无 | 帧头扩展段 `originId`（全程不改）+ `hop`（每跳 +1，>8 丢）；`originId == 自己` 立即丢并计数 |
| 诊断可见 | 无 | `auto_listen.hangs`、`loop_guard.echo_dropped/hop_dropped`、`listen_ack` |

**没做到 / 只做到一半（如实说）**
1. **辅助证据的数据源没有接线**：`observed_bt_mac` / `observed_ap` / `merge_hint` 的判定与
   「疑似同一台设备，是否合并？」面板入口都已实现，但**没有任何一端在信标里上报这两个观测值**
   （没有蓝牙扫描/AP 采集）。因此真机上这条提示**不会出现**；它不会自动合并，也不会误合并。
   若要让提示真正生效，第二阶段需要补采集（会涉及蓝牙扫描/位置权限），本轮未做。
2. **手机端 `listen_ack` 只有代码路径 + 编译 + APK 门槛**，真机"电脑发请求 → 手机开始/停止 → 电脑看到回执"
   未实测（见 8.4 第 8 条）。
3. **自回声/hop 计数**只在单测里证明；真实"蓝牙出 + WiFi 收"的环路未在真机上复现验证。
4. **静默档（三档送声的第 2 档）仍然未实现**，UI 保持灰；本轮没有顺手做（用户明确要求等点头）。
