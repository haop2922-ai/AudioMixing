# 开发过程中踩过的坑

这些不是理论，是真金白银踩出来的 —— 每一条都对应一个"看起来完全正常、
实际完全没声音"的现象。改这个项目之前建议看一遍。

---

## 一、Python 陷阱

### 1. 对 numpy 数组做真值判断会抛异常

```python
samples = decoder(pkt.payload)
if not samples:      # ← PCM 解码器返回 list，没事
    return           # ← Opus 解码器返回 numpy 数组 → 这里抛 ValueError
```

**现象**：换成 Opus 编码后点对点**完全没声音**，一换回 PCM 就好。
**为什么难查**：单元测试里直接调解码器是对的 —— 只有走接收端那条路才炸，
而异常被外层吞掉，日志上只看到"包数在涨、声音没有"。
**教训**：判空一律用 `len(x) == 0`，不要用 `if not x`。

### 2. `except` 里的兜底会把问题藏起来

```python
try:
    ...降采样...
except Exception:
    return pcm16      # 转换失败就发原格式
```

**现象**：听众流里**混着两种块长**（480 字节和 1920 字节），客户端按一种播，
另一种被放成四倍长 —— 听起来发闷、忽快忽慢。
**教训**：宁可丢掉这一块，也不要把格式不对的数据混进同一条流。

### 3. 变量名抄错作用域

GET 分支里请求体叫 `payload`，POST 分支里叫 `body`。
我照 GET 的写法抄到 POST，得到 `NameError: name 'payload' is not defined`，
接口返回 500。
**教训**：加接口分支时，连变量名一起看清，别只抄结构。

## 二、音频路线的坑

### 4. 同一块声卡只能有一个写入者

**现象**：开「只听」之后，点对点的声音**变糊甚至完全消失**，
而且和"广播那头有没有人在发"无关。
**原因**：引擎按**路由**建播放端 —— 广播通道一个、点对点一个，
两个播放端同时打开同一块设备、各写各的混音，互相踩。
空播放端也会占着设备写静音，把点对点整个淹没。
**修法**：同一块设备只让一个播放端真正持有，其他路由把混音交给它。
**教训**：路由数量 ≠ 播放端数量。按设备归并。

### 5. "音源就是输出设备本身"要分清场合

手机走蓝牙进来时，声音是 Windows 直接送到耳机的。我们再去开一路回环采集
并静音播放，只会多占一份设备和 CPU —— 听感是"越听越卡"。
但如果**有人在听广播**，就必须采 —— 否则听众那边没有数据。
**修法**：有人听才采（广播开着，或有听众连着），没人听就停。

### 6. 延迟补偿要喂和真实数据块同类型的东西

延迟补偿的实现是"先给这个设备喂一段静音，让它整体往后错开"。
我用了 `list` 而不是 float 数组，播放端直接抛异常 ——
而异常被吞掉，表现为"这一路一个字都没写"。
**教训**：往播放端写的东西，类型必须和正常数据块一致。

## 三、接口与路由的坑

### 7. 页面用 POST，接口写在 GET 里 → 404

「放行防火墙」和「监控页断开」都踩过：功能实现了，页面点按钮只拿到 404。
**教训**：页面上是 `fetch(url, {method:'POST'})` 的，接口就必须在 POST 分支里。

### 8. 插入代码前先确认自己在哪个方法里

给 POST 加分支时插进了 `do_GET` —— 于是 GET 里出现了一个只属于 POST 的变量
（`body`），Python 把它当成本地变量，**整条 GET 全部 500**。
**教训**：插入后要核对"这段落在哪个方法里"（我后来在自检脚本里加了这一项）。

## 四、设备与设备名

### 9. 别把"第一个可用的后端"当成默认后端

`default_backend_name()` 返回的是"注册表里第一个可用后端" ——
在开发机上那是 `file`。于是**所有声音被写进了文件**，两台电脑都完全没声音。
**教训**：默认输出必须显式指定 `wasapi`，不能依赖顺序。

### 10. 设备枚举和虚拟声卡

- 列设备时要跳过 `file` / `null` 这两个后端的"伪设备"（它们也有名字）
- 采集端要跳过虚拟声卡（Steam Streaming、远程桌面音频之类），
  否则采到的是空的，还容易形成回声
- 同一台机器可能同时挂着 VPN，发现包的**来源地址**未必是对方能回的地址 ——
  手机端用「数据包来源地址」比用包里的字段更可靠

### 11. 进程名和路径会变

- 程序改名后，健康检查还在找旧进程名 → 永远认为没在跑
- 防火墙规则**绑路径**：换了目录就要重新放行一次

## 五、工程习惯（这几条救过命）

1. **改代码前先留快照**：`python tools/trash.py snapshot <文件> "说明"`
   出问题一条命令取回。今天因为批量替换误删过两个方法
   （`_best_loopback_selector`、`_pick_live_capture`），当时没有快照，
   只能靠记忆重写，花了很久还出过错。
2. **打包前必须过测试**：`tools/build_exe.py` 里加了三道闸门
   （源码语法 / 单元测试 / 页面脚本），任一失败就不产出 exe。
   今天真的拦下过两次坏包。
3. **静态核对"调用但未定义的方法"**：批量改代码最容易删掉方法定义，
   编译器不管，运行时才炸。
4. **别在源码里写本机专属的设备名或机器名**：写一次就会有人复制走，
   在别人机器上静默失效。现在有测试守着这一条。
5. **测试全绿 ≠ 功能可用**：改音频链路时，一定要真的打开一次设备、
   真的推一次流。我按"测试全绿"发过一版，结果打开「只听」接口直接 500。
