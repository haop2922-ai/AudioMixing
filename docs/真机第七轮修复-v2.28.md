# 真机第七轮（PC v2.28 / 手机 2.16）

> 用户 2026-11-06 真机复测：v2.27 + 手机 2.15。本轮按"先查证根因再改，不改需求"处理；
> 逐条列定位结论、改前 → 改后判据、证据链、遗留。
>
> 版本：电脑端 **v2.28**，手机端 **2.16（versionCode 30）**。

---

## 第 2 条（最高优先）：手机视频 App 音量不影响耳机音量

### 证据链（逐条核对用户的三个问题）

| 用户问 | 结论 |
|---|---|
| 手机设置页是否真的显示 2.15 | 2.15 / versionCode 29 的 APK 已交付；本轮交付 2.16 / versionCode 30，设置页版本号由 `BuildConfig.VERSION_NAME` 直接显示。真机侧只要看到「2.16」就证明装的是本轮包。 |
| 诊断里 `vol` 随 App 音量变化时的实际数值 | v2.15 的 `vol_in_capture=true` 只告诉电脑"采到的 PCM 里已经带系统音量"，但**手机并没有把系统音量乘进 PCM**。所以诊断里的 vol 只是 App 轨道音量，不包含系统媒体音量。v2.16 起手机在发送前乘 `STREAM_MUSIC` 归一化值，`vol` 才会跟着系统音量条走（0…1）。 |
| 采集的 AudioSource 与音量读取的 stream 是不是视频 App 生效的那一路 | 采集侧：`AudioPlaybackCaptureConfiguration` + `addMatchingUsage(USAGE_MEDIA/USAGE_GAME/USAGE_UNKNOWN)`，按 **media usage** 采集（不是 `AudioSource.MIC`）。音量侧：`AudioManager.STREAM_MUSIC`。视频 App（抖音/YouTube/B 站等）的播放走 `USAGE_MEDIA` + `STREAM_MUSIC`，**与采集/读音量是同一条路**。例外：少数把对白送 `STREAM_VOICE_CALL` 的 App 不在这一路，本轮不处理。 |

### 根因

`AudioPlaybackCapture` 的采集点在**系统音量之前**（录屏语义：录到的是"内容"，
不是"扬声器实际放出来的东西"）。v2.27 的判断正好相反：它认为 PCM 已含系统音量，
于是**电脑端不再乘音量**，手机端也没乘 —— 结果两端都不乘，旋钮完全失效，只剩
"App 自己写进轨道的音量"（多数视频 App 并不改轨道音量），于是表现成"要么不响、要么调不动"。

### 关于"之前不是你提建议说只采单设备了吗"

当时提的是 **per-app 采集**（`AudioPlaybackCaptureConfiguration.addMatchingUid`），
但代码里只实现了 **usage 级**（`addMatchingUsage`），**没有实现 `addMatchingUid`**；
而且这条建议解决的是"同时采到多个 App"的串音，**与系统音量链路无关** —— 即使只采一个
App，采集点仍在系统音量之前，旋钮照样无效。所以它不是这次问题的解，也没有真正落地。
本轮不引入 `addMatchingUid`：它需要精确拿到前台 App 的 uid，且在部分 ROM 上不稳定；
当前"media usage 采集"在单 App 播放时等价于单设备采集，副作用更小。

### 修法（只做一级衰减）

- 手机 `AudioSend`：每 400 ms 读一次 `Engine.mediaVolumeRatioFor(appCtx)`，
  把 `STREAM_MUSIC` 归一化到 0…1（`getStreamMinVolume` → `getStreamMaxVolume`），
  以 Q14 乘进 PCM 再送。PCM 里于是同时含 App 轨道音量 + 系统媒体音量。
- 静音档（第 2 档）用静音**之前**的原始音量 `PREF_SILENT_ORIG`，否则"关掉本机出声"
  会连"送出去的声音"一起乘成 0。
- 电脑端保持 `vol_in_capture=true` 的语义：**不再二次乘**。全链路只有手机这一级衰减，
  不会出现"手机乘一次、电脑再乘一次"的双重衰减。

### 改前 → 改后

- 改前：系统音量 0% 与 100% 听感相同（或直接静音），耳机/电脑端旋钮无反应。
- 改后：手机按音量键，电脑端实时听到 0…1 的连续变化；App 静音时无声；手机静音档只静音本机喇叭、仍把声音送给电脑。

## 第 5 条（回归）：勾上「只听」连声音都听不到

### 定位结论：**listen 判定不是读错，是接收端准入把点对点流整条丢掉了**

证据（本机脚本复现，两个真实 UDP 节点）：

1. 发送端是广播（`broadcast=true` 的统计）：A 开「只听」→ 频道通配路由非空，收到音频 ✓；
2. 发送端是**点对点**（手机单独点了「送声音」，统计里 `send_mode=1` / `broadcast=false`）：
   - `routes_for_sender()` 返回空集合 → **一个播放端都不挂**；
   - `_stream_is_accepted()` 同时返回 False → 包被准入直接丢掉；
   - 这时「只听」开或不开都一样 —— 所以用户听到的是"彻底没声"。
3. 发送端（对方电脑）本身确实拿到了路由并一直在发包；`packets_received` 在增长，
   说明不是"发送端没拿到路由"，而是**接收端把流挡在门外**。

### 为什么是 v2.27 的回归

v2.27 把广播路由收窄成"只返回频道通配路由"（`routes_for_sender` 的 broadcast 分支），
本意是让广播只走频道。但它先把点对点分支挡在前面：声明了点对点的流直接返回空集合。
以前有具名/自动收听路由时还能靠 `specific` 那一条接住；这两条一叠加，
"手机点对点送 + 电脑开只听"就变成必然静音。

### 修法

- `routes_for_sender()`：`specific` 仍然最优先；随后 **`config.listen` 为真时返回频道通配路由**，
  只有没开「只听」时才走"未接受点对点 → 空集合"。
- `_stream_is_accepted()`：`config.listen` 为真 → 直接放行；没开「只听」→ 保留原准入闸门。
- 语义边界写进用例：**「只听」= 用户明确说"我全都听"**（来者不拒）；
  **没开「只听」** 时，未接受的点对点仍然一个播放端都不挂（Q2 的防偷听没有消失）。

### 改前 → 改后

- 改前：sets「只听」→ 静音；必须再给那台手机单独建「收听」路由才有声。
- 改后：只要勾上「只听」就立刻有声音；具名路由仍优先，不会双路叠音。

## 第 3 条：蓝牙设备不被当成节点，不能合并

### 根因：后端拿**图节点键**去查注册表，永远查不到

关系图发的是 `lan:<node_id>` / `bt:<名字>`，而 `registry.get()` 要的是裸 node_id。
v2.27 直接把 `lan:xxx` 丢给 `registry.get()`，所以每次拖拽合并都回
「找不到要合并的局域网设备（请等它上线后再拖）」—— 用户看到的就是"软件不让我合并"。

### 修法

- 新增 `_graph_key_id()`：`lan:` / `peer:` 前缀统一剥掉；`bt:` 保留（蓝牙快照没有 node_id，
  走"仅面板合并"那条路径）。
- `relation_merge()` / `relation_split()` 都先过这一步。
- 布局版本号 `REL_LAYOUT_V` 从 `3` 升到 `4`：旧坐标一次性作废，`bt:` 卡片不再停在画布外
  只剩一条绿箭头（用户图 1 里 `瘾控` 的样子）。

### 改前 → 改后

- 改前：拖动蓝牙卡到 WiFi 卡 → 弹"找不到设备"，合并不上。
- 改后：拖上去就进合并确认；合并后一张卡、可「拆开」，路由一条不删。

## 第 4 条（图 1）：关系图依旧乱穿

### 根因（两层）

1. v2.27 用 Tarjan 强连通分量 + 最长路径分层：两台互相送过（点对点 + 自动收听各一条）
   就落进同一个 SCC、拿到**同一层**，边只能画成"右侧一条弧"；
2. `relPos` 把旧坐标存在 localStorage 里，升级后没有失效，本机被固定在右边、
   对方在左上 —— 叠加起来就是用户看到的"从本机右侧绕上去、又钻进对方右侧"。

### 修法

- `relComputeRank()` 重写为**以本机为参照的双向 BFS**：
  - 上游（声音送到本机）沿入边反向走，层级 0、-1、-2… → **源在左**；
  - 本机第 0 层 → **在右**；
  - 下游（本机送出去的，如蓝牙耳机）沿出边正走 → **更右**。
- `relAutoPos()`：`x = 22 + (rank - minRank) * span`，同层内往下堆。
- `relDrawLinks()` 按**层级**选端口，不再看当前 x：
  - 正向 `rb > ra`：源右边缘 → 目标左边缘（**左进右出**）；
  - 反向（回环）：`relReturnPath` 从上/下方绕回，进目标右边缘，绝不从右侧钻进正向卡片；
  - 同层：右侧小弧。
- `REL_LAYOUT_V = '4'` 清掉旧坐标。

### 改前 → 改后

- 改前：本机右下、对方左上，蓝线从本机右侧绕上去又进对方右侧；互送的两台同列。
- 改后：所有源在左列、本机在右列（下游更右）；正向边从源卡片右侧进目标卡片左侧；
  回环单独一条返回弧。

## 真机复验清单（用户）

1. 手机装 2.16（设置页应显示 2.16）；电脑换 v2.28。
2. 手机放视频，按音量键：电脑输出应连续变大变小；App 内静音应无输出。
3. 电脑勾「只听」：不等任何"收听"路由，立刻能听到对方（手机广播或点对点都算）。
4. 关系图：源在左、本机在右；正向边左进右出；互送只出现一条回环返回弧。
5. 蓝牙卡（如 `瘾控`）：能拖到对应 WiFi 卡上合并、能「拆开」。

## 明确遗留（不修的原因）

- **`STREAM_VOICE_CALL` 类 App**：音量不跟 `STREAM_MUSIC` 走，本轮不覆盖。
  原因是该路需要按 App 判断通话/媒体用途，误判会把正常音乐乘成 0。
- **per-app（`addMatchingUid`）单 App 采集**：未实现。原因是需要前台 App uid，
  且部分厂商 ROM 上 `addMatchingUid` 不稳定；当前 media usage 采集在单 App 播放时
  等价于单设备采集。
- **防火墙规则里 v2.19–v2.25 的旧 exe 路径**：`audit_leftovers` 只报 warning。
  这些是 Windows 防火墙的历史入站规则，留着不影响运行；删除需要管理员权限且
  会改变用户既有网络策略，本轮不动。
