> 上一轮已通过的第 3/4/5/6(部分)/7/9/10/12/13/15/16/17/18 条没有重做。

## 结论先行

1. **第 1 条（虚线节点变多）已修**：路由判定从「端点当前不在线 = stale」改成三态
   `missing / no_data / offline / ok`。只有**对端身份确实不存在**（本进程从没见过、连续 60 秒解析不到）
   才会画红虚线并进入「清理失效路由」；真设备只是关机/换网 → 灰实线；两端在线但这一路暂时没声音
   → 琥珀实线 + 标注。现场"虚线变多"的根因就是旧判定把 `offline` 也当成了 `missing`。
2. **第 8 条（挂断状态与时间不匹配）已修**：挂断记录的「已 N 秒没消息」改成**实时增长**，
   卡片按钮只在真的收到音频时才显示「✓ 收听中」，有路由没数据时显示「… 已连 · 等数据」，
   新音频一到立刻清掉旧的"已挂断"记录。
3. **第 11 条（手机开智连约 20 秒才接收）已修**：PC 建好发送会话就**立刻**推 `listen_req`
   （不再等 2 秒统计节流、允许首包未发时也推）；手机打开智连的瞬间按缓存统计**立即**开收。
   目标 ≤2 秒，实际值需真机确认（见"没做到的部分"）。
4. **第 14 条（关系图连线错）已修**：布局改为**按有向层级左进右出**（Tarjan 强连通分量 +
   最长路径），非回环边一律"源在左、目标在右"；Wi-Fi 蓝 / 蓝牙绿 / 广播橙 / no_data 琥珀 /
   offline 灰 / missing 红虚线 / 回环红粗线；每条边带箭头；`u===v` 自环不画。
5. **第 2 档（送声 + 手机静音）已按用户授权实现**：只把 `STREAM_MUSIC` 临时降到 0，
   音频数据**完整继续发送**；停止/切档/退出/崩溃/断连都有还原路径，且唯一音量调用集中在
   `Engine.applySilentVolume()` 一处，便于审计。

## 一、4 项逐条表

### 第 1 条（回退）：关系图「虚线节点」反而变多

| 项 | 内容 |
|---|---|
| **现象** | 真机上「不在线 / 不可达」的虚线节点比上一版更多；有些明明刚才还在送声音的设备也被画成虚线。 |
| **根因** | 上一版 `_refresh_route_staleness` 只要**有任意一个端点当前不在线**，累计 60 秒就标 `stale`。这把两类完全不同的情况混成一种：① 对端身份真的不存在（旧 id / 脏配置 / 重装换了 id）；② 真设备只是关机、换网、休眠、暂时没数据。后者本来会回来，却被画成"幽灵"。另外它没有查本进程的 `ever_seen`，所以"见过面的真设备"也会被判死。 |
| **改了什么** | `audiomixing/engine.py`：重写 `_refresh_route_staleness` 为三态判定；新增 `_route_has_traffic()`（按收/发流最近一包判断，静音也算有流）；`routes_json()` 输出 `state / stale / no_data / offline`，其中 `stale` **只在 missing 时为真**。前端 `relLinkClass()` 按状态映射线型，`relBuild` 不再一刀切 `if(r.stale) return`。 |
| **改前 → 改后怎么判断** | 改前：`no_data` 和 `offline` 都会变虚线，图上看不出"暂时没声"还是"已不存在"。改后：<br>· 两端在线、这一路暂时没数据 → **琥珀实线** + "暂无数据"标注；<br>· 见过面的真设备关机/换网 → **灰实线** + "离线"；<br>· 本进程从没见过的 id，连续 60 秒解析不到 → **红虚线** + 进入「清理失效路由」；<br>· 有音频在流 → 蓝/绿实线。 |
| **现场为什么"变多"** | 不是脏配置变多，而是**判定过宽**：把"真设备暂时离线"算成了"节点不存在"。旧 id 残留只是少数；用户看到数量上涨，主因是手机休眠/换网后 60 秒就被画成虚线。 |

### 第 8 条：挂断状态与时间不匹配

| 项 | 内容 |
|---|---|
| **现象** | 约 30 秒跨度的截图里，卡片仍写"收听中"或"已自动收听"，但诊断里的"音频静默 / 心跳"秒数与实际对不上；有时反过来——声音已经回来了，卡片还挂着"已挂断"。 |
| **根因** | ① 挂断记录里的 `audio_silence_s / heartbeat_s` 是**判定那一刻的快照**，之后不再增长，所以截图越晚越对不上；② 卡片按钮只按"路由是否存在"显示「✓ 收听中」，不看是否真的有音频；③ 挂断记录在"已经收到新音频"后没有立即清除，导致"已挂断"与"真的在收"同时存在。 |
| **改了什么** | `engine.py`：`auto_listen_state()` 里把挂断秒数按 `当前时间 - 判定时间` **实时累加**，心跳优先用注册表现值；`_queue_auto_listen()` 收到新音频立刻 `_auto_listen_hangs.pop()`。`index.html`：按钮文案改为 `flows.in_receiving ? '✓ 收听中' : '… 已连 · 等数据'`，挂断时仍显示「已挂断 · 待命」。 |
| **改前 → 改后怎么判断** | 改前：截图停在"音频静默 4.2s / 心跳 4.5s"却写收听中；改后：30 秒后诊断就是约 30 秒，按钮同时变成「已挂断 · 待命」；音频一回来，挂断标记立刻消失并回到「✓ 收听中」。 |

### 第 11 条：手机开智连后约 20 秒才开始接收

| 项 | 内容 |
|---|---|
| **现象** | 手机端打开「智连」，电脑对它「送声音」，约 20 秒后才开始接收；目标 ≤2 秒（第一个请求/第一个包就接）。 |
| **根因** | ① PC 只在 `_send_peer_stats` 的 2 秒节流里带 `listen_req`，而且**只给已经出过包**的会话报；刚建好会话的那几秒里对端收不到请求。② 手机端打开智连后不会立即按已有统计判断，只能等下一份统计包（再叠加丢包/节流时就更久）。③ UDP 请求没有额外重试窗口，首包丢了只能等下轮。 |
| **改了什么** | `engine.py`：建好发送会话后立即 `push_peer_stats_now()`；`_send_peer_stats` 在 `force`（刚改路由/刚建会话）时允许 `packets_sent<=0` 也带 `listen_req`；周期性统计仍每 2 秒重发同一请求，作为丢包重试。`Engine.java`：`toggleSmart()` 打开时立刻 `applySmartNow(host)`，用缓存里的最后一份 `PeerStats` 直接走 `handleWantListen`。 |
| **改前 → 改后怎么判断** | 改前：打开智连后盯着手机，20 秒左右才跳"接收中"。改后：打开智连时对方已经在送 → 立即进入接收；刚点"送声音" → 首个请求在会话建立瞬间发出，正常局域网应在 2 秒内。回归测试 `test_pc_pushes_listen_req_immediately_when_sender_starts` / `test_phone_applies_smart_immediately_on_toggle`。 |

### 第 14 条：关系图能检测回环，但连线画错

| 项 | 内容 |
|---|---|
| **现象** | 图上的线方向和节点位置矛盾：有的箭头/连线从右往左、和"发/收"语义相反；不同链路颜色相同；回环检测结果与画面不一致。 |
| **根因** | 旧布局把"本机"固定在第 0 列、局域网第 1 列、蓝牙第 2 列，与边的真实方向无关。`A→B` 且 `B→A` 时两条线从同一侧出发，叠在一起；节点在左却要指向右边的目标时，线被硬画成反向。 |
| **改了什么** | `index.html`：新增 `relComputeRank()`（Tarjan 强连通分量 + 分量间最长路径），`relAutoPos()` 按层级从左到右排；非回环边一律从**源右边缘 → 目标左边缘**，回环返回边单独画右侧弧；新增 `REL_ARROWS` 箭头 marker 与 `relLinkClass()` 状态色；`u===v` 自环在 `relBuild` 里直接跳过。旧本地拖拽坐标用 `wl-relpos-v=3` 一次性作废，避免升级后仍按旧列位显示。 |
| **改前 → 改后怎么判断** | 改前：同一对手机互送时两条线重叠、方向看不出。改后：来源在左、去向在右；回环边红色粗线且能看出"绕回来"；颜色图例：蓝=Wi-Fi、绿=蓝牙、橙=广播、琥珀=暂无数据、灰=离线、红虚=失效、红粗=回环。 |

## 二、第 2 档（送声 + 手机静音）单独一节

### 现象 / 需求
用户要求"第 2 档 = 手机扬声器不响，但音频照常发给电脑"，不是静音这条流、不是停止采集。

### 实现
- 手机端 `Engine.applySilentVolume(boolean)`：**整个工程唯一**调用 `setStreamVolume` 的地方。
  - 进入时先 `getStreamVolume(STREAM_MUSIC)` 取原值，把「原音量 + 进入时间 + active 标记」用
    `commit()` **同步落盘**，然后把 `STREAM_MUSIC` 置 0。
  - 只动 `STREAM_MUSIC`；铃声/通知/通话流一处都不碰；**不使用** `setStreamMute`（避免把用户锁死在静音）。
  - 已经在 0 时不重复写，避免每 150ms 骚扰系统。
- 发送链路完全不动：`AudioSend` 照常采集、照常发包；第 2 档只改音量。
- 循环：`0 → 1 → 2 → 0`。第 1 档再按一次进第 2 档；第 2 档再按一次回第 0 档（停止并还原）。
- 文案：按钮 `送声中 · 手机静音`；长按/详情写明"手机会静音、声音仍在传给电脑、退出或停止自动还原、其它 App 的媒体声也会一起哑"。

### 还原路径（全部覆盖）
| 路径 | 处理 |
|---|---|
| 停止送声（逐台停止最后一台） | `setSending` → `syncSilentVolume()`；`sendingActive=false` → 还原 |
| 切到第 0 / 第 1 档 | `setSendMode` → `syncSilentVolume()` → 还原 |
| 广播关闭 / 广播+逐台都停 | `setBroadcasting(false)` → 还原 |
| 音源关闭 / 采集不可用 | `syncSenderTargets` 里 `sourceEnabled=false` → 还原 |
| 对端全部掉线 / 蓝牙断开 / 换网 | `sendingActive=false` → 还原 |
| 服务销毁 / 退出 App | `Engine.stop()` → 还原 |
| 进程被杀 / 异常退出 | 下次启动构造函数先 `restoreSilentVolumeIfNeeded()`，读残留标记立即还原并清除 |

### 怎么验（真机）
1. 第 1 档送声，手机扬声器有声音；再按一下进入第 2 档 → 手机扬声器静音，**电脑仍在出声**，手机界面/PC 监控里采样计数继续增长。
2. 调出系统音量条确认媒体音量为 0；按回第 0 档 → 音量恢复原值。
3. 第 2 档状态下直接退出 App（最近任务划掉）→ 重新打开，媒体音量已自动恢复。
4. 第 2 档状态下重启 App（模拟崩溃后重开）→ 启动即恢复原音量。
5. 第 2 档时手机播音乐/视频：其它 App 的媒体声也一起哑（预期副作用，不是 bug）。

### 已知副作用与边界
- **手机其它 App 的媒体声音也会一起变哑**：本应用采集的就是系统媒体声，没有独立播放通道，做不到只压这一路；这是用户明确接受的代价。
- 第 2 档期间用户手动把音量调上来，系统会以用户操作为准（本应用不会每 150ms 强行按回 0）。
- 如果用户在第 2 档时**直接关机/拔电池**，系统音量会保持 0 到下次开机；下次打开本 App 会按残留标记还原。这是"崩溃兜底"的边界，已在报告如实写明。

## 三、没做到 / 只做到一半（如实）

1. **第 11 条的"≤2 秒"不能只靠单测证明**：本轮验证的是"请求下发时机"和"手机开智连立即应用缓存"，
   真正毫秒级延迟受局域网、UDP 丢包、手机省电策略影响，**必须真机确认**。
2. **第 8 条的真机 30 秒截图**无法在这里复现：单测验证了秒数实时增长、按钮跟随 `in_receiving`；
   卡片文案最终效果需真机截图确认。
3. **第 1 条的 missing 不会"立刻从图上消失"**：本轮按用户最新要求落实为"红虚线 + 一键清理"；
   如果用户希望连虚线也不画、直接隐藏，需要再改一次（当前保留可见是为了让用户知道配置为什么失效）。
4. **第 2 档的"退出 App"依赖服务销毁路径**：正常退出/划掉会走 `stop()`；如果被系统直接杀进程，
   依靠下次启动的残留标记兜底，不能保证"杀进程瞬间就还原"。
5. **audit_leftovers 是 0 error / 3 warning**：3 个 warning 都是历史遗留（旧版本 exe 的防火墙规则、
   `.tmp` 开发目录、promo 素材），本轮遵守"不删 `.tmp`、不动用户进程/防火墙"未处理。
6. **第 2 档的真机音量行为**无法在 CI 里跑：只做了源码级断言（唯一调用点、还原路径、0→1→2→0、
   崩溃标记），实际音量需真机确认。
