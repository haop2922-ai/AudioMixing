## ④ 电脑关了，手机还在往里发声音

**用户原话**：「我发现在手机蓝牙向电脑传输音频的情况下，电脑关闭应用。手机声音还在向电脑发送」

### 电脑端的根因
发送端的目标表**只在用户点选的那一刻写一次**，对方关机 / 退出 / 换网络之后没有任何人把它拿掉。
更糟的是 `PeerEndpoints.online` 对**手动添加**的对端**恒为 True**（连发现层的 15 秒超时都不生效），
所以那种对端会被永远当成"在线的"。

### 修法（宽限期 12 秒）
判据只有一条：**最近还有没有它的任何消息**（UDP 没有握手，手机也不回 PING，"能不能连上"问不出来）。

| 证据 | 来源 |
|---|---|
| 发现信标 | `peer.age_s` |
| 控制包（手机每 2 秒一次的 T_STATS） | `receiver.control_messages`（带到达时刻） |
| 它正在给我们发音频 | `receiver.stats()["streams"]` |
| HTTP `/api/status` 探测成功 | 只对"眼看要被判死"的对端探一次 |

四条里任意一条新鲜就算活着 → `PEER_SILENCE_GRACE_S = 12.0` 秒内不会被误判（Wi-Fi 抖动丢几个信标不影响），
超过 12 秒立刻停发，并在面板上说明：

> 已停止向「已关机的手机」发送：它已经 15 秒没有任何消息（关机 / 退出程序 / 换了网络）。

★ 清理跑在**引擎自己的后台循环**里（`tick()` 每 0.5 秒 → `apply_routes()` → `_track_peer_liveness()`
→ `desired_senders()`），**不依赖面板是否打开** —— 手机端 task-17 的真根因正是"清理挂在界面 tick 上，
一锁屏就停"，电脑端不能犯同样的错。有一条端到端测试专门钉这件事（不开任何页面）。

## ① 自动收听 + 两端音量条同步 + 修"电脑端滑块无效"

**用户原话**：「我希望发送按键被按下后，收听设备会自动收听。双方设备的音量条保持同步。
（本次手机向电脑传输声音中。电脑的音量条改动无效）」

### 协议（★ 与手机端 task-17 逐字对齐 ★）
复用现有 `T_STATS`（ptype=7）的 JSON 负载，**不新增包类型、不改 28 字节包头**，老版本忽略未知字段即可：

| 字段 | 类型 | 语义 |
|---|---|---|
| `want_listen` | bool | 我在把声音送给你，请自动打开收听。**幂等**：还在送就一直 true |
| `gain` | 0~1.50 | 我→你 这条链路的共享音量（= 我的「我送它的」= 对方的「我听它的」） |
| `gain_ts` | int 毫秒 | 上面那个值最后一次被改的时刻 |
| `gain_rx` | 0~1.50 | 你→我 这条链路的共享音量（= 我的「我听它的」= 对方的「我送它的」） |
| `gain_rx_ts` | int 毫秒 | 同上 |

两边各报各自两个方向的值，所以每条链路有两个视角，靠时间戳判新旧、**无回环**。实现要点：
- 时间戳**按整数解析**（`_as_ms`），绝不经过浮点 —— 手机端踩过 13 位毫秒被截断成 1.7e8 的坑；
- 值一样时只对齐时间戳、**不回推**（否则两端互相弹）；
- 本机 0.8 秒内刚动过这条 → 不抢（用户正在拖）；
- **时钟偏差兜底**：本机 5 秒没动过，就采纳对端的值。

### 自动收听（可撤销，不静默改设置）
- 收到 `want_listen: true` → 自动建一条 `它→本机` 的路由，带 `auto` 标记 + 标签「对方请求收听（自动）」；
- 面板顶部明说：**「📡 M332BF 请求收听本机 —— 已自动打开（对方请求收听（自动））。这是对方按了「送声音」时自动加的，不是你自己加的。」** + 「撤销」按钮；
- 撤销 = 删掉这条自动路由 + 把这台设备写进**「永不再自动」名单**（与手机端同名行为）；
- 再请求时只提示不自动加：**「📡 M332BF 请求收听 —— 你之前关过它，所以没有自动打开。要听它的话，点右边。」** + 「这次打开」按钮；
- 总开关「**自动接受收听请求**」（默认开）：关掉后请求只提示，理由写「你已经关掉了「自动接受收听请求」」。

### ★ ①-3「电脑端音量条改动无效」的真实原因（Lead 猜的方向对，机制不一样）
不是"netmic 不是路由所以没有可改对象"这么简单 —— 真正的原因是：
**手机送进来的声音根本没有走"路由"这条路。**
- 手机一开始发声音，「正在发送的手机自动播放」就把它收编成**频道音源**（`channel_sources` + `local=True`）；
- 之后声音走的是**本机直通/频道**那一路（或 `mic.gain × channel_gain`），**没有路由对象**；
- 而卡片上的滑块（v1.11）只会改"路由的 gain"，此时 `inRoute` 是 undefined → 滑块是**禁用**的，
  拖它当然"无效"。
- 蓝牙那条路更直接：手机蓝牙进 Windows 的是 **A2DP 采集设备**，更不可能有路由。

所以修法是让滑块**按实际存在的层找对象**，并在滑块旁标出调的是哪一层：

| 优先级 | 情况 | 调的是 | 面板标注 |
|---|---|---|---|
| 1 | 有 `它→本机` 的路由 | 那条路由的 gain | 这条路由 |
| 2 | 它是网络音源（netmic，Wi-Fi 手机） | 这台手机的采集增益 `/api/mic/gain` | 这台手机送进来的 |
| 3 | 它是频道/直通正在采的音源（含蓝牙 A2DP） | 频道音量 `/api/settings {channel_gain}` | 频道音量（所有音源共用） |
| — | 都没有 | 禁用 + 悬停说明 | 不可调 |

行为已验证（Node 里把页面脚本跑起来，直接问它"这台设备该调哪一层"）：
```
① netmic + 无路由              → {"kind":"mic","tag":"这台手机送进来的"}
② A2DP 采集设备 + 无路由       → {"kind":"channel","tag":"频道音量（所有音源共用）"}
③ 有 它→本机 的路由            → {"kind":"route","id":"r1","tag":"这条路由"}
④ 什么都没有                   → null（滑块禁用，写"不可调"）
```

## ② 详细档离线保留 1 分钟；简洁档不动

**用户原话**：「当这个设备在局域网中离线时。你在第二部分标签页等待一分钟，如果还没有上线的话就移除。
第一部分标签页不动（原设计好看且合理的）」
- 只改**详细档**那张表：离线的设备保留 **60 秒**（`OFFLINE_KEEP_S = 60`），状态列写
  **「已离线 32 秒（等它回来，满 60 秒才移除）」**，整行灰掉、地址用警告色；
- **简洁档一个字没动**；
- Discovery 的 15 秒超时是发现层的，**没有动它**。

## ③ 第七部分（蓝牙设备区）上下不对齐

**用户原话**：「第七部分标签页蓝牙设备上下不对其好难受啊」
原因：那些行是 `flex` + 名字列 `auto` 宽 —— 每行名字长度不同，后面的状态胶囊和按钮就一行一个位置。
现在 ⑦ 蓝牙 / ⑧ 网络音源两个列表改成同一套栅格：名字列固定 `minmax(96px,150px)`，
状态胶囊与按钮各自对齐（`justify-self:start` + 最小宽度），窄屏回落成两列。
只作用于这两个列表，③ 本机状态那几行不受影响。

## 顺手修掉的一个真 bug（后端自动加载）
`audiomixing/audio/base.py::_autoload()` 原来写的是"注册表非空 = 已经加载过"：
任何一处先 `import` 了单个后端（engine 里就有 netmic），其它后端就**永远不加载** ——
之后要开 `null`（模拟/测试音）或 `wasapi`（真实声卡）时直接
`unknown audio backend 'null' (have: netmic)`，表现是**什么都打不开、一点声音都没有**。
2026-10-14 在测试里稳定复现。现在改成"按名字逐个补齐"，并且**不用 reload**
（reload 会造出新的类对象与新的模块级字典，别处还攥着旧引用 → "设备列表永远是空的"）。
回归测试用 AST 钉住"不许再出现 `if _BACKENDS: return`"。

## 只有用户能验的
1. 手机按「送声音」→ 电脑面板是否**自己**开始收听，并显示「已自动打开」+「撤销」；
2. 两端拖同一条音量条，另一边是否跟着变（同一个值）；
3. **蓝牙那条路**：手机蓝牙放歌 → 电脑面板上那台设备的「我听它的」滑块现在能调（标注为频道音量）；
4. 手机点「停止发送」/关掉 App → 电脑这边 12 秒内停止发送（面板出现"已停止向…发送"）；
5. 详细档里拔掉一台设备的网，看它是否灰掉并显示「已离线 N 秒」，满 1 分钟才消失；简洁档不变。
