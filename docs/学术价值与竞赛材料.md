## 一、真实的技术点（都是有据可查的，不是包装）

### ① 跨平台实时音频协议的一致性验证 —— 最能写成学术味的一条

同一个 28 字节包头，**手机端用 Java 写一遍、电脑端用 Python 写一遍**。
二进制协议各写一遍最容易出的问题就是"看起来一样、实际差一个字节，然后永远连不上"。

我们用的办法不是读代码，而是**逐字节对拍**：

```
Java 端构造 5 个样例包（普通音频/空负载/seq 回绕/控制包/空包）→ 打印 hex
Python 端构造同一组样例                                    → 打印 hex
两边 hex 逐字符相同 → 5/5 整包一致
```

后续又加了一道**收包准入测试**：把**电脑端真编出来的 1948 字节**喂进手机端的接收路径，
验证"已收包 1 / 坏包 0 / 建流 1"。这在软件测试里叫**差分测试（differential testing）**，
是跨平台协议实现里正儿八经的手段。

**可写的题目**：轻量级跨平台实时音频协议的实现与一致性验证

### ② 实时音频缓冲算法的"可测试性改造" —— 我认为这是最亮的一条

手机端的抖动缓冲（32 槽环形缓冲 + 按包序预缓冲 + 主动压延迟 + 丢包补静音 + 断流恢复）
跑在安卓框架上，**原本无法在桌面 JVM 里测试**。

我们的做法：写一个脚本**按大括号配平，把 `Stream` 类从真源码里原样抽出来**，
只做两处机械替换（类修饰符、时钟来源），在桌面 JVM 上跑 **31 项断言**。

```
断流 2.5 秒再恢复   → [OK] 恢复后重新出声 48 帧（修复前是 0 帧）
seq 从 65535 回绕   → [OK] 错位 0 帧、误判丢包 0 次
乱序到达            → [OK] 仍按序播出
持续过载（每 tick 3 包） → [OK] 深度封顶 190ms 并回落
```

★ **这套测试当场抓出一个真 bug**：`nextSeq = -1`（哨兵值）被函数末尾无条件的自增推成 `0`，
播放头在空缓冲上空转，对端恢复后新包全被判"太超前"丢掉 —— **断一次就再也不出声**。

同类还有第二个：压延迟逻辑"每 tick 只丢一帧然后 return"，而对方每 10ms 正好来一帧，
于是收一帧丢一帧，缓冲区永远降不下来 —— 实测 5946 个包里 5908 个被这么丢掉，
**表现是"连上了、数字都在动、就是没声音"**。

**可写的题目**：移动端实时音频算法的可测试性改造与离线回归验证

### ③ 异构 Wi-Fi 下局域网设备发现的可靠性

浏览器不能发 UDP 广播，所以"自主发现"这件事在 App 里做。我们实测发现：

```
手机 74 秒只收到 8 个信标，而对方按 2 秒一次应该发了约 37 个
→ 安卓 Wi-Fi 省电会大量丢弃组播/广播帧
```

应对是**三种手段叠加**：组播 `239.255.77.120` + 子网定向广播 + **对已知设备额外单播**。
最后一条是关键：**只要互相见过一次面，单播这条路就一直通**（单播帧不被 AP 的组播过滤丢）。

**可写的题目**：异构 Wi-Fi 环境下局域网设备发现的可靠性改进

### ④ 免虚拟声卡的桌面音频采集

Windows 上采集"系统正在播放的声音"，主流方案（VoiceMeeter + VBAN 等）都要求装虚拟声卡。
我们直接用 **WASAPI Loopback**，免安装、免重启，并处理了"配置里记着的设备已被拔出/空转"时
自动回退到可用设备。这一条工程性强于学术性，但在比赛里是**用户能直接感知的差异点**。

### ⑤ 面向非技术用户的端到端可观测性

一个真实数据：本项目的绝大多数缺陷，都是**用户贴一份诊断报告**定位的，不是靠反复问。

诊断报告覆盖三层：本机信息 / 发现层（信标收发、自己发的信标绕回来几份、组播网卡）/
传输层（收包、坏包分类、缓冲深度、流数）/ 播放层（每路电平、欠载）。
**坏包还给来源 IP、长度分布和前 16 字节 hex**。

★ 这条的学术味在于：**把"用户描述现象"变成"用户提供数据"**，
是可用性研究里"降低 bug 报告成本"的典型做法，而我们有一个完整的真实案例。

**可写的题目**：消费级音频工具的端到端可观测性设计与实证

## 三、三个创新点怎么写（对比式写法，评委最认）

```
创新点 1：跨平台协议用"逐字节对拍"保证一致，而不是靠代码评审
  对比：同类项目通常只在单一平台实现，或两端用同一套库（掩盖实现差异）
  证据：5 个样例整包 hex 完全相同；收包准入用对方真编的字节验证

创新点 2：把跑在手机框架里的实时音频缓冲算法做成可离线回归的测试资产
  对比：多数移动音频项目的缓冲逻辑"只能靠真机试"，回归靠人肉
  证据：31 项断言 + 当场抓出两个真机级 bug（断流不恢复、压延迟死循环）

创新点 3：局域网发现用"组播 + 广播 + 单播兜底"三层，针对安卓 Wi-Fi 省电丢帧的实测问题
  对比：常见做法只用组播或 mDNS，在省电策略下会周期性"设备消失"
  证据：实测 74 秒只收到 8 个信标 → 引入单播兜底
```

## 六、答辩必被问的三个问题（提前准备答案）

**Q1：这不就是个音频工具吗，创新点在哪？**
> 单看功能确实像。但如果只看功能，就看不到两件事：
> 一，跨平台的二进制协议是两端各写一遍的，我们用逐字节对拍保证一致，而不是"能跑就算对"；
> 二，跑在手机框架里的实时缓冲算法，我们把它做成了可以在桌面离线回归的测试资产 ——
> 这两条当场抓出了两个"连上了却没声音"的真机 bug。
> 我们的创新在**验证方法**上，不在功能清单上。

**Q2：市面上有 Snapcast / VoiceMeeter / 手机自带投屏，你凭什么？**
> 它们的定位和我们不同：Snapcast 要自己提供音源、VoiceMeeter 每台机器都要装虚拟声卡、
> 手机投屏是镜像画面顺带捎声音。我们做的是"**局域网内任意设备的声音送给任意设备**"，
> 免虚拟声卡、免服务器、免账号，而且**源和目标都是集合**（多对多）。
> 另外一个差异：**我们不做跨网络** —— 这是有意为之，因为一旦跨网络就必须有中转服务器，
> 那就不再是局域网工具了。

**Q3：用户量多少？商业价值呢？**
> 诚实回答：目前是开源项目，没有商业模式。它的价值在于**解决问题的通用性** ——
> 我们在开发中定了一条硬规则：不对任何特定设备做专项优化，所有设备走同一条逻辑
> （为此还专门写了一个测试来防止代码里出现具体设备名）。
> 如果一定要谈价值，是"替代一批各自要装虚拟声卡的方案"这件事本身。

## 八、一句话给评委的版本

> 我们做的不是一个"能传声音的软件"，而是一套**能被验证**的局域网音频系统：
> 跨平台协议用字节对拍保证一致，跑在手机框架里的实时缓冲算法被抽出来做离线回归，
