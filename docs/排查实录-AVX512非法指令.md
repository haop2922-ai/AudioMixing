# 排查实录：0xc000001d（非法指令）—— 产物只在编译机上能跑

> 2026-10-21。v2.1 和第一版 v2.2 在另一台电脑上双击完全没反应；
> 最终查明是 **AVX-512 的 memcpy 被链接进了 exe**，目标 CPU 不支持。
> 这份记录按“看到什么 → 排除了什么 → 真凭实据 → 怎么修 → 怎么验”写，
> 方便下次再遇到“打不开 / 没反应”时少走弯路。

---

## 1. 症状

用户原话：**“之前输出的 V2.1 版本换了其他人的电脑就打不开，无论是双击还是右键以管理员身份运行。”**

现场特征：

```
· Windows 11，Intel Core Ultra 5 125H，中文账户；
· 双击 exe：没有任何窗口、没有报错、没有托盘图标；
· 右键“以管理员身份运行”：同样没有任何反应；
· 任务管理器里只能看到残留的旧进程，没有正常服务；
· %APPDATA%\AudioMixing\launcher.log 根本不存在。
```

`launcher.log` 不存在这一条非常关键：说明程序**根本没进入 Python**，
不是“Python 里某个 import 失败后静默退出”。

---

## 2. 第一次误判：中文账户路径

用户先怀疑是中文账户路径（`C:\Users\<中文名>\...`）。这个怀疑很合理，
因为构建机是英文账户，目标机是中文账户，而且单文件版启动时要往 `%TEMP%`
解压自己。

于是做了三组对照（都用同一个 exe、同样的哈希）：

```
A. ASCII exe + 中文 TEMP / 中文 APPDATA / 中文配置目录   → 能启动 ✓
B. 中文 exe 路径 + ASCII TEMP                          → 能启动 ✓
C. 免解包版 + 中文路径 / 中文 TEMP                     → 能启动 ✓
```

还补了一组**完整双击链路**（不是 serve）：中文 TEMP、中文 APPDATA、
中文 `USERPROFILE`、中文 exe 目录，结果服务、Edge 监控窗、托盘全部正常。

**结论：中文路径不是这次的根因。** 中文兼容性仍然要做（日志、自检都保留了），
但不能把“中文账户”当成结论。

教训：

```
✗ 不要用“我觉得是路径问题”直接改代码
✓ 先做“同一个文件换目录 / 换调用者 / 换环境”的对照实验
✓ 没有 launcher.log 的“双击没反应”，优先怀疑“进程没进 Python”
```

---

## 3. 真凭实据：Windows 事件日志

让对方在目标机跑了一键诊断（`AudioMixing-诊断.bat`），报告里的
`Application Error` 直接给出了答案：

```
出错应用程序名称：AudioMixing.exe，版本：2.2.0.0
出错模块名称：    AudioMixing.exe，版本：2.2.0.0
异常代码：       0xc000001d
错误偏移：       0x0000000001296fd3
```

同一份报告里还有 v2.1 的记录：

```
出错应用程序名称：Audio Mixing v2.1.exe，版本：2.1.0.0
异常代码：       0xc000001d
错误偏移：       0x000000000001bdb3
```

`0xc000001d` = `STATUS_ILLEGAL_INSTRUCTION`（非法指令）。
两个版本、两个完全不同的打包形态（单文件 / 免解包）都崩，说明问题不在
“解压”“路径”“杀软”，而在**编译出来的机器码**。

---

## 4. 反汇编：崩溃点是一条 AVX-512 指令

把 v2.2 的 exe 按 PE 段表做 RVA→文件偏移转换，再反汇编崩溃偏移：

```
RVA 0x1296fd3 -> file 0x12963d3
0x12963d3: 62 f1 7c 48 10 02    vmovups zmm0, zmmword ptr [rdx]
0x12963d9: 83 e1 40             and ecx, 0x40
0x12963dc: 49 29 c9             sub r9, rcx
0x12963df: 62 f1 7c 48 10 14 0a vmovups zmm2, zmmword ptr [rdx + rcx]
...
```

`zmm` 是 AVX-512 的 512 位寄存器。目标机 Intel Core Ultra 5 125H（Meteor Lake）
**不支持 AVX-512**，执行到第一条 `vmovups zmm0` 就直接非法指令。
v2.1 单文件版的崩溃偏移 `0x1bdb3` 反汇编出来是**同一个 memcpy 函数**，
所以两个版本崩得一模一样。

进一步统计 `.text` 段：

```
v2.1 单文件 stub：95 条 zmm（AVX-512）指令
第一版 v2.2 免解包：95 条 zmm 指令
```

---

## 5. 为什么只在编译机上能跑

构建机是 **AMD Ryzen 7 9800X3D**，支持 AVX-512；Nuitka 4.3 用 **zig** 做 C 编译。
问题出在两层：

1. **zig 的 compiler-rt 是链接阶段选实现的**。只给
   `CFLAGS=-mcpu=baseline`，Nuitka 自己生成的 C 代码是 baseline，
   但链接时仍会从 compiler-rt 里选一个 AVX-512 的 `memcpy`。
2. **构建脚本没有声明 baseline**。产物默认按“编译机能跑”的指令集生成，
   换到不支持 AVX-512 的 CPU 上就 `0xc000001d`。

实测对照：

```
只加 CFLAGS=-mcpu=baseline          → 仍能看到 vmovups zmm0（AVX-512 未清零）
CFLAGS + LDFLAGS=-mcpu=baseline     → .text 里 0 条 zmm
```

**关键就是 LDFLAGS**：链接命令也要带 `-mcpu=baseline`，否则 compiler-rt
仍然选 AVX-512 版本。

---

## 6. 修法

### 6.1 构建环境

`tools/build_nuitka.py` 的 `build_env()`：

```python
env["CFLAGS"] = "-mcpu=baseline"
env["CXXFLAGS"] = "-mcpu=baseline"
env["LDFLAGS"] = "-mcpu=baseline"
```

`nuitka_args()` 显式指定：

```python
"--zig",
"--target-arch=x86_64",
"--standalone" ...   # 或 --onefile
```

### 6.2 发布门禁

新增 `check_portable_isa(exe)`：

- 解析 PE，取 `.text`；
- 若出现已知的 AVX-512 memcpy 特征 `62 f1 7c 48` → 直接 FAIL；
- 若安装了 capstone，逐条反汇编所有 `0x62`（EVEX）候选，统计带 `zmm` 的指令；
- 只有 `zmm == 0` 才允许继续打包。

构建日志会打印：

```
[build] 可移植性检查: AVX-512(zmm) 指令 0 条 => PASS
```

### 6.3 回归测试

`tests/test_audiomixing.py` 新增 `test_build_forces_a_baseline_cpu_isa`，
钉住：

```
CFLAGS / CXXFLAGS / LDFLAGS 都含 -mcpu=baseline
nuitka_args 里含 --zig 和 --target-arch=x86_64
```

## 8. 这次顺手修的两个诊断工具坑

1. **BAT 带 UTF-8 BOM**：cmd 会把 BOM 当成命令的一部分，报
   `'锘緻echo' 不是内部或外部命令`。BAT 必须是**无 BOM** 的 ASCII/GBK。
2. **`%~dp0` 尾部反斜杠**：BAT 把 `"C:\...\AudioMixing\"` 传给 PowerShell，
   闭合引号被反斜杠转义，PS1 收到的是带引号的非法路径，
   `Resolve-Path` 报“路径中具有非法字符”，后面所有检查都拿不到 exe。
   修法：BAT 不传目录参数，PS1 自己取脚本目录，并在入口去掉尾部斜杠/引号。

## 9. 教训（下次别再踩）

1. **构建机的 CPU 特性不是目标机的**。只要构建机支持 AVX-512 / AVX2 / 新指令，
   就必须显式把产物压到 baseline，并**扫描二进制**确认，而不是只看编译参数。
2. **CFLAGS 管不到链接阶段**。zig 的 compiler-rt 必须用 `LDFLAGS` 一起压。
3. **“没有 launcher.log + 双击没反应”先查事件日志**。`0xc000001d`、`0xc00000fd`
   这类代码比任何猜测都快。
4. **不要用一个假设替代证据**。中文路径、杀软、打包方式都可能是“看起来很像”
   的原因；真正定案要靠事件日志、反汇编、对照实验。
5. **交付门禁要扫最终产物，不是扫源码**。源码在编译机上没问题，
   链接器换一个 memcpy 实现就能让产物在目标机必崩。
